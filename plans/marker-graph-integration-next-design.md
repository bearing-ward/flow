## Decision

Accepted 090 settles the standalone configuration representation. It does not settle graph integration or arbitrary native marker resource ownership. Shared endpoint widening cannot safely be dispatched as another core-only child: all three renderers, default application, explicit saved envelopes, patch transport, Foldkit revision comparison and real Model/ports must move together.

The full registered-name integration has a concrete public capability blocker in installed Foldkit 0.163.0. An asynchronous caller OnMount failure is caught inside the SDK and printed, without a definition-owner failure callback. The reviewed registry contract requires removing that definition's usable URL and releasing its resources while healthy definitions and accepted graph remain unchanged. That behavior cannot be inferred from console output, a try/catch around content construction, or an injected builder wrapper. Arbitrary caller Html may already contain Mount actions constructed outside that wrapper.

Recommendation: resolve the public SDK failure-reporting boundary through a separately reviewed capability decision before implementing the full native registry. Preserve the approved registration signatures and arbitrary SVG/resources contract. Do not silently replace them with a restricted builder or cooperative caller protocol.

There is a possible earlier coordinated child for built-in strings, standard configuration objects and transport. It would leave every non-built-in string unregistered and apply the already-approved missing-name no-URL diagnostic policy, without publishing any registry option. Its mounted graph/save/patch/Model behavior would be real integration, but registered-name, arbitrary caller Mount containment and MiniMap requirements would remain pending. This is a sequencing option for root and cold review, not a chosen executable packet or a waiver of those requirements. It also depends on an accepted global-color policy and an exact accepted native-geometry input. Until those inputs and that scope are reviewed, no endpoint widening is executable.

## Vetted findings

### [ARCHITECTURE-01] Resolve public ownership of asynchronous caller Mount failure

- **Evidence**: R `node_modules/foldkit/dist/mount/index.d.ts:45-49` exposes MountAction name/args and `f(element, viewStateChanges): Stream`, with no failure observer. R `node_modules/foldkit/dist/html/index.js:1017-1038` runs the action in a captured Runtime context, catches the Cause and calls console.error. R `node_modules/foldkit/dist/mount/index.d.ts:1-12` provides MountTracker started/ended observations, not a failure cause. R `node_modules/foldkit/dist/runtime/crashUI.d.ts:4-26` describes unrecoverable crash reporting after the dispatch loop stops, not per-definition recovery. M `plans/marker-minimap-continuation-design.md:171-173` requires failed URL withdrawal, resource release, healthy survival and generation guards.
- **Impact**: Flow cannot learn which already-mounted arbitrary caller definition failed through the inspected public registration path. Its URL may remain usable despite a failed resource, and cleanup/publication cannot be coordinated by definition generation. Console reporting establishes neither these outcomes nor an inevitable whole Runtime crash.
- **Effort**: L for a reviewed public SDK capability and actual native integration proof; no honest local-only fix estimate is available.
- **Risk**: HIGH. A dependency change or registration restriction could alter replay, dispatch ownership, asynchronous cleanup and caller compatibility.
- **Confidence**: HIGH for the installed path and absent reporting parameter on the inspected public APIs. Runtime outcomes remain unexecuted in this investigation.
- **Fix sketch**: Obtain a supported SDK failure observation boundary that covers arbitrary nested caller Mounts and carries actual owner/resource identity. Require native proof before claiming containment. If only cooperative callers can report failures, return for explicit registration-contract review instead of treating that as equivalent support.

### [ARCHITECTURE-02] Coordinate endpoint widening with actual renderers

## Public capability assessment and recovery options

Foldkit's content registration is proposed as `(context, h) => Html`, with optional native attributes and adapter-owned root, M `plans/marker-minimap-continuation-design.md:163`. R `node_modules/foldkit/dist/html/index.d.ts:61-62` defines Html as VNode/null and Child as Html/string. Its builder OnMount at `:2673-2675` receives an action, but the returned Html is already rendered VNode data, not a public list of resource actions available to the parent definition owner. The production marker at `:151-164` carries mount name/args/message mapping for inspection, not the failing action, Cause or fiber handle.

A caller may close over a different builder, use a helper's preconstructed child or render a nested submodel. The SDK describes builder closure ownership at `html/index.d.ts:2696-2722`. Wrapping only the h supplied to content therefore has no demonstrated authority over every returned child's Mount. Traversing and replacing VNode hooks, using runtimeInternals/`__` helpers, monkey-patching the SDK or intercepting console is excluded. A test-only Mount marker walker cannot supply production failure ownership.

If Flow possesses an action before it is built, the public MountAction.f permits a checked Stream wrapper. Mount.mapMessage only maps successful messages, R `mount/index.js:94-96`; it does not catch failure. A Flow-owned action wrapper can contain that specific action's typed failure/defect, provided generation and cleanup are tested. This limited possibility does not cover arbitrary actions already embedded by caller code, so it cannot discharge the retained registry contract.

MountTracker.end is not a failure event. The actual OnMount implementation invokes release notification during destroy/replay release at R `html/index.js:998-1010`, while the failure handler only prints at `:1025-1026`. A generic Runtime crash reporter also cannot stand in for per-definition failure observation. No assertion here assumes either inevitable crash or automatic healthy-definition survival.

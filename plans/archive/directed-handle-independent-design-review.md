# Independent architecture review of Plan 078

Decision after amended-policy recheck: **APPROVE** for the bounded named-handle architecture. The original review requested revision; Plan 078 and the supplement now preserve null-resolved physical IDs, and Plan 078's independent-review amendment explicitly resolves the direction/helper/recovery clarifications. This is design approval, not implementation acceptance or member closure.

Reviewed on 2026-09-30 against the main checkout's actual production source, Plan 078 and the 067 connection supplement. This review changes only this document. No tests, builds, captures, source edits, or frozen 065 candidate edits were performed. Source inspection establishes design constraints; it does not establish runtime acceptance.

## Original required amendment: preserve the physical identity resolved from null

Plan `078-complete-directed-handle-integrity.md:100-102` and supplement `directed-connection-design-supplement.md:98` resolve null to the first canonical named declaration and then omit its stored endpoint ID. This conflicts with supplement `:60`, which requires new interactions to store the selected physical IDs, and with Plan 078's no-silent-ID-omission boundary at `:88,148`.

The current renderer uses declaration order whenever the endpoint ID is absent (`packages/core/src/domain/flow-edge.schema.ts:52-70`). The current constructor stores the resolved IDs (`packages/core/src/domain/flow-connection.schema.ts:185-198`). Consider a null source request with canonical declarations `[A, B]`: it resolves to A. Omitting the accepted edge's sourceHandle then changing the declarations to `[B, A]` retargets that edge to B. A versioned save cannot restore A once its identity has been omitted. Strict/loose independence does not prevent this change.

Replace Plan 078's paragraph at `:102` and the persistence sentence in supplement `:98` with this contract:

> A null public request selects the first current canonical named declaration at the request boundary. Store that resolved declaration's explicit branded ID in the accepted edge and retain it in every supported save/restore projection. Preserve supplied null only in the separate public request/callback projection whose contract requires it. A physical handle projection retains its real named ID. Existing caller-supplied edges with absent or own-undefined endpoint IDs retain their established declaration-order fallback; creating an edge from a null request does not create another absent-ID edge.

This is an intentional native difference from pinned addEdge's deletion of null endpoint keys (`research/artifacts/xyflow/0a1f9575b25679f2880175de8d3eae21aedde921/packages/system/src/utils/edges/general.ts:166-171`). Its reason is preserving the physical selection made by a request in Flow's single accepted graph. Do not claim exact stored-edge projection conformity for this null-request case.

Required proof: issue null and explicit-A requests against the same declarations and show the same resolved duplicate identity; accept one edge; reorder canonical declarations; toggle host strict/loose; save and restore the supported format; show that its accepted IDs and measured endpoints still select A in all three hosts. Separately prove that an originally absent-ID edge continues to follow first-canonical declaration order. Public callback null, resolved handle A, accepted edge A, and persisted edge A need separate assertions. Missing canonical fallback fails atomically. Keep nullable physical Handle/NodeHandle declarations and measurement identity migration held with their original owners.

## Clarify reconnect direction and the canonical helper

Plan 078 `:36-42,48` has the correct separation: fresh gestures construct direction once; validation receives directed input; reconnect changes only the selected directed endpoint. Make that separation explicit in the ordered implementation/proof steps, including these cases:

- Fresh target-origin gestures use destination as source and initiator as target once. Pinned XYHandle constructs that direction directly (`research/artifacts/xyflow/0a1f9575b25679f2880175de8d3eae21aedde921/packages/system/src/xyhandle/XYHandle.ts:298-313`). Reconnect never passes its already-directed candidate through the gesture constructor or canonical helper.
- Loose reconnect of a stored target-target edge, and of an edge whose source declaration is target-kind and target declaration is source-kind, preserves the unchanged endpoint's node and physical ID. Cover replacement of each endpoint independently, callback/proposal direction, controlled acknowledgement, and repeated validation.
- Strict validation checks the complete candidate under the plan's existing rule. If the unchanged endpoint is noncanonical, reject atomically and retain the original edge; do not swap it into canonical direction or silently grandfather it. This preserves the stored edge while applying strict eligibility to the proposed replacement.

These are necessary production checks: core reconnection currently ignores the validator's returned connection and patches the selected endpoint (`packages/core/src/domain/flow-reconnection.schema.ts:54-81`). Vue independently normalizes the candidate, emits that normalized callback, and overwrites both endpoints of the resulting edge (`packages/vue/src/flow-canvas.ts:2872-2939`). Updating only the core reconnect function would leave the Vue direction bug active.

Also make Plan 078 `:40` preserve the public helper's mode contract explicitly: omitted/strict mode returns the supplied connection unchanged; loose mode swaps only a resolved target-kind source paired with a resolved source-kind target; either same-kind pair and missing declarations remain unchanged. Then the helper is idempotent without reversing directed same-kind input. Its current export is public (`packages/core/src/public.ts:454-464`), and its current strict branch is already identity (`packages/core/src/domain/flow-connection.schema.ts:61-85`). Prove omitted mode, strict mode, all four loose kind pairs, missing declarations, and repeated application through installed public probes. Direct validation must never invoke this helper. The present validator and issue finder both invoke normalization (`:88-94,156-166`); remove both internal uses in the same slice.

## Approve explicit identity and frozen reader boundaries

The proposed graph/resolver change correctly separates an accepted physical identity from interaction capability. Current live integrity conflates these by rejecting an explicit declaration with a different endpoint kind (`packages/core/src/domain/flow.schema.ts:302-323`), and current geometry filters kind before ID (`packages/core/src/domain/flow-edge.schema.ts:52-70`). Resolve a defined ID by equality across kinds, reject a missing ID, retain canonical declaration-order fallback only for absent/own-undefined IDs, and keep host mode out of stored geometry. No measurement schema or additional graph authority is needed.

The frozen reader matrix in Plan 078 `:70-88` is required and approved. The immutable oracle rejects explicit endpoint-kind mismatches but skips absent IDs (`packages/conformance/src/fixtures/legacy-v1-persistence/baseline-reader-writer.js:368-403`), then applies that integrity workflow after both document and session envelope decoding (`:1051-1064`). The current production decoder instead calls live decode directly (`packages/core/src/domain/flow-persistence.ts:163-175`). Generalizing live integrity without the frozen endpoint guard would expand v1 acceptance. Add the narrow compatibility guard before live decode in both current legacy readers and additive decode1; additive decode2 uses generalized live integrity. Keep the oracle independent and immutable.

The new format code and precedence in Plan 078 `:60-68` are approved for valid accepted documents: origin first, native fields second, resolved explicit noncanonical identity third. Current origin/native order is `packages/core/src/domain/flow-persistence.ts:102-123`. Own-undefined endpoint IDs are absent; stored null remains schema-invalid. Missing node/ID must not be classified as the new format extension or emitted as a supported2 graph. Keep separate invalid-input fixtures and valid combined-extension fixtures so error precedence does not conceal integrity failures. No claim that the historical legacy encoder already enforced full graph integrity is needed.

## Clarify recovery after a legacy snapshot failure

Plan 078 `:94,124` requires a later request to succeed, but does not state the state/channel transition that makes success possible. The existing Foldkit SnapshotRequest always attempts a legacy save of the accepted graph (`packages/foldkit/src/application.ts:1811-1829`). An unchanged noncanonical graph must fail every legacy request with the same format reason; a later request ID alone cannot make it serializable.

Specify two proofs: after the first correlated legacy failure, a fresh legacy request against the unchanged noncanonical graph fails independently while Runtime stays alive; after an acknowledged replacement with a canonical graph, a fresh legacy request succeeds. Once additive070 is integrated, separately show an additive request against the original noncanonical graph succeeds through the same owner/client. No automatic downgrade, retry-as-success, alternate store, or second client. Preserve matching-once settlement, foreign/duplicate/late-event filtering and disposal tests.

## Scope and acceptance

After the null-identity amendment and explicit clarifications above, the named directed-handle architecture is approvable. Retain Plan 078's same-slice generalized integrity/frozen guard requirement and the activation dependency on migrated additive observers. This review approves no source implementation, semantic member closure, Plan 067/070 DONE status, generic069 contract, unnamed074 field, or original076/065 measurement identity change.

## Conformity and deviations

**Source-derived conformity, runtime unverified:** fresh gesture orientation and strict/loose eligibility follow the pinned XYHandle boundary. **Proposed intentional differences:** accepted explicit-ID geometry is independent of capability kind, including target-target rendering where pinned source-kind lookup may fail (`research/artifacts/xyflow/0a1f9575b25679f2880175de8d3eae21aedde921/packages/system/src/utils/edges/positions.ts:34-56`); null requests retain resolved named IDs in accepted/persisted edges to preserve physical identity across declaration reorder. Both differences require public production/output proofs and particular original-member mappings. **Preserved compatibility:** frozen v1 endpoint-kind and omission behavior, literal1 envelopes, and existing unknown-key stripping remain separate from expanded live/v2 semantics. **Unverified/held:** all runtime execution, complete browser/packed/reference gates, genuine unnamed declarations, generic payloads, and parent-family closure.

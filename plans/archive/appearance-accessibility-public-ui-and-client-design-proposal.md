## Findings that the design must address

### [LIFECYCLE-01] Prevent public UI resurrection and late writes

- **Evidence:** A `packages/foldkit/src/ui.ts:669` reattaches background and controls without a disposed guard; `:688` removes them without closing `ensureMounted`. At `:586`, a pending zoom refresh resumes into button writes; `:617` and `:627` run callbacks after asynchronous actions without a lifetime check.
- **Impact:** A retained mount can resurrect removed controls. An operation started on an old mount can update detached controls or call an application callback after teardown.
- **Effort:** M, including retained-reference and deferred-response native browser tests.
- **Risk:** MED; changing callback timing and refresh suppression can expose callers depending on late completion.
- **Confidence:** HIGH for the source gaps; actual runtime manifestations require browser proof.
- **Fix sketch:** Give each mount a closed lifetime and refresh generation. Check both after every await and before all DOM changes, callbacks and reattachment.

### [OWNERSHIP-02] Replace fixture-specific Runtime DOM repair with a public native lifecycle

- **Evidence:** H `apps/foldkit/src/appearance-config-test.ts:223` appends controls itself; `:235` observes and repairs Runtime-managed canvas children. A `apps/foldkit/src/main.ts:325` already coordinates public UI mounts through a native composition entry; `:374` derives MiniMap input from `acceptedStates`. A `packages/foldkit/src/ui.ts:316` provides a separate public viewport portal with an owned disposer; its observer at `:392` observes the entire document.
- **Impact:** The historical appearance fixture proves its private repair arrangement rather than a reusable public appearance mount. Copying its observer into every consumer gives the fixture another DOM lifecycle to maintain.
- **Effort:** M, including native demo and installed-consumer migration.
- **Risk:** MED; Runtime patches can remove host-appended children, and replacement canvases require a new mount rather than reparenting an old one.
- **Confidence:** HIGH for the ownership mismatch; the proposed scoped repair mechanism remains unverified.
- **Fix sketch:** Extend the existing public canvas UI mount to own its optional MiniMap, appearance subscription and bounded DOM repair. Retain application composition and accepted-state projection ownership.

### [PROTOCOL-03] Order accepted appearance snapshots by producer revision

- **Evidence:** H `packages/foldkit/src/application.ts:301` has no response revision; `:1879` captures one configuration per successful request. H `packages/foldkit/src/appearance-client.ts:42` removes the resolver before notification; `:45` replaces its cache with every matched successful response; `:64` settles only after subscribers.
- **Impact:** A late older success can roll a client backward. A subscriber that disposes the client can leave the currently removed resolver unresolved. Reentrant notifications have no bounded publication order.
- **Effort:** M for producer/schema/client changes and adversarial transport plus real Runtime tests.
- **Risk:** HIGH; this changes public correlation, result types and model serialization contracts.
- **Confidence:** HIGH for missing protections; the new protocol is a proposal, not accepted behavior.
- **Fix sketch:** Add one producer-owned revision, preserve captured responses, and drain matched results while settling the current resolver before a stable subscriber batch. Keep all other queued resolvers visible to disposal.

### [LIFECYCLE-04] Tie native client settlement to an explicit composition owner

- **Evidence:** H `packages/foldkit/src/appearance-client.ts:20` receives only port handles; `:106` treats a failed send as disposal. D `dist/runtime/hostConnector.d.ts:3` specifies validation failures and no-op sends after disposal; `:41` exposes only ports and `dispose`, with no disposal subscription. A `apps/foldkit/src/main.ts:567` closes native helpers, but that function itself does not call the raw Runtime disposer.
- **Impact:** Raw Runtime cancellation can stop the producer without settling a ports-only client's promises. A successful no-op send after cancellation does not reveal the cancellation; a decode failure does not prove disposal.
- **Effort:** M, including already-aborted, in-flight and subscriber-triggered close tests.
- **Risk:** MED; consumers must use the composition's close operation to obtain the settlement guarantee.
- **Confidence:** HIGH for the public API limitation.
- **Fix sketch:** Bind native resources to a composition-owned AbortSignal outside serialized state/ports. Close those resources before invoking the original Runtime disposer; retain the raw-dispose limitation explicitly.

### [COMMIT-05] Acknowledge through the actual public Runtime commit boundary

- **Evidence:** H `packages/foldkit/src/application.ts:709` immediately emits appearance responses. D `dist/runtime/runtime.js:270` changes the live Model and schedules a later render; `:235` forks commands asynchronously. D `dist/render/render.d.ts:15` defines the actual commit wait; `dist/render/render.js:53` falls back to a frame when no Runtime commit service is present.
- **Impact:** An immediate response can precede matching DOM output. A unit invocation outside Runtime can appear to wait while exercising only the fallback. Coalesced updates make an old response snapshot different from the latest committed DOM.
- **Effort:** M, including an embedded Runtime DOM/revision probe.
- **Risk:** MED; adding a render wait changes response timing and exposes disposal during that wait.
- **Confidence:** HIGH for the available public API and historical omission; production integration remains unverified.
- **Fix sketch:** Yield public `Render.afterCommit` inside the actual response Command, then emit its captured result. Define acknowledgment as committed or superseded by a later committed appearance revision.

## Recommended public native mount contract

The caller continues to use `mountFlowCanvasUI` from `@flow/foldkit`. It supplies its native canvas, existing viewport client, one native lifetime and its existing graph/viewport projections. It never imports private Runtime rendering services or appends controls/MiniMap itself. This is a signature sketch for review, not checked TypeScript:

```text
lifetime = new AbortController()
runtime = Runtime.embed(createProgram(...initialConfiguration))
appearance = createAppearanceClient(runtime.ports, { signal: lifetime.signal,
  initial: initialConfiguration })
ui = mountFlowCanvasUI(canvas, viewportClient, {
  ...existingControlsOptions,
  owner: { root: stableNativeOwner, signal: lifetime.signal },
  appearance,
  miniMap: { graph: derivedGraph, viewport: derivedViewport }
})
ui.updateMiniMap(nextDerivedGraph, nextDerivedViewport)
closeOwner() // native composition's idempotent close, including raw runtime.dispose
```

`FlowCanvasUIOptions` retains existing background/controls options. A new appearance-enabled option variant requires both `owner` and `appearance`; the optional MiniMap also belongs to that variant. `owner.root` is the caller's stable native host around this Runtime instance, containing the supplied canvas, not `document` or a global selector. The native AbortSignal and appearance methods never enter Graph Model, Effect Schema JSON, ports or persisted documents. Existing ordinary mounts retain their public entry point, but every mount receives the disposed/epoch protections. New native callback/config types must follow the repository's Schema-derived contracts and existing host-local function precedent; declarations above do not authorize casts or duplicate schema interfaces.

The mount owns its background, controls, optional MiniMap, event listeners, appearance subscription, abort subscription and one scoped MutationObserver. It borrows the clients. Disposing a canvas mount unsubscribes from them but does not dispose borrowed clients or cancel graph authority. `getCurrent` supplies a detached configuration projection; initial seed output is provisional until the client's initial real `get` succeeds. Interactive appearance controls are disabled during bootstrap and pending updates. The mount subscribes before it starts bootstrap `get`, so a synchronous response cannot be missed; the client constructor itself does not start an unobserved request. Returned mount methods include the existing `ensureMounted`, `updateViewport`, `dispose`, plus `updateMiniMap(graph, viewport)` for an owned optional MiniMap. No optional MiniMap means that updater has no visual effect; it cannot create a second MiniMap behind the caller's back.

The MiniMap owns a derived rendering projection, as A `packages/foldkit/src/ui.ts:427` already does. It does not maintain an accepted document, execute acceptance or independently calculate movement. `acceptedStates` remains the authority; native composition derives `FlowGraphView` with the accepted measurement map and passes it to this public updater. Reuse the existing real paths at A `apps/foldkit/src/main.ts:374`, `:390`, `:394` and the measurement result composition. Consolidating the two existing public mounts removes duplicate MiniMap disposal from the application. It does not replace accepted-state observers or turn appearance publications into accepted graph events.

The mounting contract is tied to the original canvas identity. Before installing resources, verify the root contains that native canvas and the signal is live. An already-aborted signal returns a closed mount without subscriptions, observers, DOM insertion or requests. Register abort cleanup before any request can be issued, and check the signal again before initiating bootstrap. The observer watches `owner.root` with `childList`/`subtree`, not the entire document. At a post-mutation callback, close the mount if the original canvas no longer belongs to this root or is disconnected. A removed/replaced canvas is terminal for that mount, even if somebody retains and later reinserts it. A root removed as a whole may produce no mutation within that root; composition must abort its lifetime when removing its root. This scope does not promise automatic external ancestor-removal detection.

Otherwise `ensureMounted` repairs only this mount's original owned nodes, only when their direct parent is not the original canvas. It never moves a node already owned by another canvas or adopts a replacement canvas. Direct-parent identity checks mean observer delivery caused by its own repair performs no further DOM changes; do not rewrite attributes, reorder correctly mounted nodes or render the MiniMap on every observer callback. Appearance subscriptions update labels synchronously on a changed configuration; graph/viewport calls render changed projections separately. Disposal marks closed and increments its epoch first, disconnects the observer and abort subscription, unsubscribes appearance, removes event listeners, disposes MiniMap/controls and removes owned nodes. All later retained `ensureMounted`, update and event-handler calls are inert. Observer delivery already queued before disconnect must also check the closed lifetime.

Use the existing `mountFlowViewportPortal` ownership precedent at A `packages/foldkit/src/ui.ts:353` and `:367` for idempotent cleanup. Do not copy its document-wide observer at `:392`; it solves a different removal boundary. The chosen root scope needs its own native isolation proof.

## Native composition and asynchronous work

At A `apps/foldkit/src/main.ts:325`, retain native pane discovery and replacement detection. On pane replacement, close the previous canvas mount, then mount a new public instance with the same still-live runtime owner and current derived projections. At `:361`, capture the particular mount and its generation before awaiting `getViewport`; after awaiting, require owner live, that exact mount still current and response not disposed before updating it. Do not dereference the mutable latest mount after the await and apply an old response to it. The existing measurement observer's callback at A `packages/foldkit/src/measurement-observer.ts:153` may call native reconciliation, but cannot become the appearance fixture's private child-repair mechanism. Public UI's own bounded lifecycle handles UI children through unrelated later Runtime patches.

Controls use a disposed flag, mount epoch and refresh generation. Capture these before each viewport or appearance await; check them immediately after it, before callbacks, label/disabled writes or further requests. Read `getViewport` when status matters rather than `getZoom`, which exposes only a number. Each refresh request has a generation so a slower earlier refresh cannot overwrite a newer result. Interactive controls derive pressed state from the current client configuration's OR of draggable/connectable/selectable; an acknowledged update changes all three together. Completion reads the client's latest projection rather than painting the response's possibly superseded configuration. Invalid, failed or disposed operations do not fabricate a toggle or invoke successful-action callbacks. No new request begins after the owner is closed. UI disposal alone suppresses late UI effects; borrowed-client pending settlement belongs to the enclosing native owner.

The application's close operation sets its closed flag/epoch first, aborts the signal synchronously, disposes current UI and appearance clients idempotently, unsubscribes accepted/viewport/measurement projections, disposes existing viewport/measurement/native helpers and settles their existing pending maps, then calls the original `Runtime.EmbedHandle.dispose` exactly once. Abort handlers must not issue new port requests. Preserve the existing cleanup at A `apps/foldkit/src/main.ts:572` through `:602`, and route pagehide plus the fixture's explicit close through that one owned close operation. Retain the raw handle privately in this composition; do not monkey-patch its disposer. Its public fixture surface exposes owner close, not a purported automatically observed raw cancellation.

`createAppearanceClient` installs its abort subscription before any pending insertion/send, handles an already-aborted signal synchronously, and checks closed status before sending. This is an actual local close signal, not a synthetic producer acknowledgment. Local disposal results state that no response was observed; they do not claim an in-flight mutation was rejected or rolled back. A mutation might have entered the producer before close. Tests must distinguish that uncertainty from a real invalid response's failure atomicity.

Calling raw `runtime.dispose()` independently cannot guarantee a ports-only facade's settlement. D `dist/runtime/hostConnector.d.ts:7` makes later sends no-ops; there is no public runtime death subscription. The UI's scoped observer may detect resulting canvas removal and close its own mount, but cannot reconstruct or acknowledge client requests. This limitation is unavoidable without an explicit owned close contract or a separately reviewed Runtime API change. A timeout does not prove cancellation and is not the proposed mechanism.

## Producer-owned revision and Model migration

Add one application Model field `appearanceRevision`, Schema-derived nonnegative safe integer, initialized to zero beside the selected normalized configuration. It is adapter protocol metadata, distinct from A `packages/foldkit/src/application.ts:623` acceptedDocumentRevision. Every same-owner appearance change through this public update path increments this counter once in the synchronous update reducer. Client issue sequence remains request correlation only. Neither the client nor the native fixture assigns producer revision. Different clients use the same producer counter; a new runtime owner has a new native lifetime and fresh clients so responses from a previous owner cannot be correlated to it.

Equality compares the fully normalized first-boundary schema values: exact color mode, exact booleans and each of the ten exact string keys. Empty string differs from a default string. Partial patches merge against the current normalized configuration before comparison; omitted fields retain it and own undefined rejects. Property insertion order is irrelevant. Do not use JSON string order, object identity or compare a patch directly to a full configuration. Native live formatter identity is outside this serialized equality and counter: replacing a formatter, if supported, requires its separately reviewed native lifecycle. System dark/light media state is derived output and does not increment the requested configuration revision; `colorMode: system` remains that accepted value across media changes.

| Input at producer | Model/configuration effect | Result and revision |
| --- | --- | --- |
| `get` | Same Model; no config mutation | `unchanged`, current full config and current revision |
| Valid update equal after normalization | Same Model; no increment | `unchanged`, current full config and current revision |
| Invalid patch | Same Model; no increment, no graph/viewport change | `invalid`, current full valid config and current revision |
| Valid different update | Replace appearance once; increment once; retain graph/document/viewport authority | `applied`, captured new full config and new revision |
| Native owner close / local send or validation failure | No fabricated producer transition | Local native outcome; never an acknowledgment |

All producer response snapshots carry a non-null revision. Keep the original historical producer, response schema and client as diagnostic evidence; these semantics are a new reviewed protocol rather than a silent replay of H `application.ts:1879`, which returned `applied` even for equal updates. At the maximum safe revision, an equal update remains unchanged; a different valid update returns a typed `failed` response with reason `revision-exhausted`, retaining the same Model, valid configuration and revision. Use a discriminated Schema union on the existing appearance result port, not another counter or a new port. This failure variant also requires cold approval. Never wrap or silently reuse the revision.

A `packages/foldkit/src/application.ts:617` and Graph Model at A `packages/foldkit/src/graph.ts:185` have neither appearanceRevision nor appearance. The migration test must use actual counterless accepted 087 Model JSON from its real exported `initialModel`/`ModelSchema` serialization, with meaningful existing state, and decode it through the successor's real Model schema. It cannot use a hand-shaped `{ graph: {} }` stand-in. Missing new configuration uses the documented canonical default; missing revision uses zero. Preserve all existing document, control mode, measurement, gesture and acceptedDocumentRevision fields. An already present configuration/revision is preserved and validated. Malformed present values and own undefined reject; do not catch all failures and reset the model. The default is a Model migration policy, not permission to silently reset existing native fields.

Use Effect RC116's key-only decoding defaults, with encoding `passthrough`, so new encodings retain the counter. The inspected actual declaration is A `node_modules/effect/dist/Schema.d.ts:4596` and `:4605`; allowed options are `omit`/`passthrough`, and own undefined is not absence. Existing H models/configurations are unaccepted diagnostic inputs, not an assumed compatibility promise. No native formatter, AbortSignal, DOM node, subscription or resolver is serialized. Saved FlowDocument persistence remains independent from transient adapter Model serialization.

## Real commit acknowledgment

The proposal changes H `packages/foldkit/src/application.ts:709` so its real `RespondAppearance` Command yields `Render.afterCommit` from public `foldkit` exports before `Port.emit`. D `dist/index.d.ts:16` exposes Render and `dist/render/public.d.ts:1` exposes afterCommit. Run this effect inside the actual Runtime command scope supplied by `Runtime.makeElement`; do not import, fake or provide the private RenderCommit service. Outside that runtime context the implementation at D `dist/render/render.js:53` uses a frame fallback, which cannot prove a model commit.

An `applied` result means its configuration transition was accepted by the producer, and its corresponding mutation has committed **or has been superseded by a later committed appearance revision**. A `get`/`unchanged`/`invalid` result reports a configuration snapshot at request processing, followed by the same commit boundary. None promises that DOM at receipt equals every older result snapshot. Acknowledgment is not paint, native assistive-technology delivery or external telemetry delivery.

For native testing, expose the producer revision as a renderer-derived data attribute on the existing application root, e.g. `data-flow-appearance-revision`; A `packages/foldkit/src/application.ts:2539` already renders that root. The attribute reads the sole Model counter and is changed by the actual VDOM commit, not by the client or fixture. It requires explicit cold-review approval as part of the scoped application view change. A real embedded-runtime probe must send two different updates before the same render frame, await their results, and observe committed DOM revision at least each acknowledged revision. At the latest committed revision assert matching actual role/name/description and public control/MiniMap labels. For an older result, permit the later configuration in DOM; separately assert its captured response retained the original configuration and revision. Capture actual response order rather than assuming forked Commands complete FIFO.

## Client publication, correlation and settlement

Keep a pending record per exact opaque requestId, installed before send. The ports are bound to this one runtime owner. An unrelated result has no matching pending record and does not change configuration, revision, listeners or pending count. The first matched result is queued for that record; subsequent duplicate deliveries for it, whether queued or already settled, have no effect. The request counter is never reset/reused within the client lifetime. Public port validation remains the transport boundary; the native facade validates external update input before sending.

Use a synchronous, single-owner response drain with a reentrancy guard. A queued record remains in pending until its drain step starts. In that step, compute the result/cache decision, remove and settle that one record exactly once **before** notifying subscribers, then publish to a stable registration snapshot. Promise continuation scheduling does not replace the explicit settlement rule. Subscriber exceptions are caught individually and logged at the existing failure boundary without dumping configurations. Registration identity matters: a callback unsubscribed and re-added during the batch is a new registration and must not receive the old batch. New subscriptions join the next batch. Check registration live and owner live before each callback. Reentrant synchronous results append to the queue and drain only after the current subscriber batch; they do not recursively change the configuration halfway through that batch.

Disposal during a subscriber closes the client, unsubscribes transport/abort/listeners, empties the response queue and settles every still-pending request with a local disposed outcome. The current result already settled remains its honest producer result. Requests initiated reentrantly before disposal remain in the pending map and are therefore settled. The drain checks its epoch before advancing to another record and resets its guard in a finally boundary. Calls after close settle locally without sending. None of these local results pretends a producer ran after cancellation.

The client stores only an observed configuration/revision projection. A supplied initial configuration is a provisional seed; before the first real response the observed revision is unknown. Bootstrap `get` establishes observation before interactive controls become active. Do not treat revision zero plus a constructor default as evidence that it matches an already existing producer. The proposed wire `AppearanceResponseSchema` has requestId, status (`applied`/`unchanged`/`invalid`), full configuration and nonnegative safe-integer revision, plus a separate discriminated `failed` variant with the same snapshot fields and reason `revision-exhausted`. Native `AppearanceClientResultSchema` is a discriminated union: `origin: producer` carries those original fields; `origin: client` carries requestId, local status (`invalid`/`disposed`/`failed`), detached last-observed configuration, nullable last-observed revision, and a reason (`invalid-input`, `owner-closed`, `send-rejected`, or `revision-conflict`). Before first observation, the local configuration is explicitly the provisional seed and revision is null. A local outcome never has producer origin. Derive types from these schemas; the wire never contains AbortSignal, callback or local resolver. This result-shape change, including retaining disposed as a native-only status, is an explicit cold-review decision. Retain simple status handling in the fixture, but do not flatten validation failure into fake runtime disposal as H `appearance-client.ts:106` does.

| Matched authoritative producer snapshot | Cache/publication | Own request settlement |
| --- | --- | --- |
| First observed revision | Adopt full validated snapshot; establish revision | Original response |
| Greater revision | Adopt it; notify only when normalized configuration changed | Original response |
| Equal revision, equal configuration | No duplicate publication | Original response |
| Lower revision | Preserve latest cache/revision; no rollback or publication | Original captured response, honestly superseded |
| Equal revision, conflicting normalized configuration | Preserve cache; structured protocol failure, no publication | Typed native failure identifying the conflicting revision; never fabricated `applied`/`invalid` |

`invalid` producer replies contain the producer's current valid configuration. Their revision can exceed this client's cache if another client's successful update occurred first. Treat that higher valid snapshot as an authoritative observation while retaining the request's `invalid` status; the rejected patch itself causes no Model mutation. This publication distinction needs explicit review and a two-client test. Local invalid replies have no authoritative producer snapshot and never update cache. Equal-revision different payload is a protocol violation because the producer increments on each different accepted configuration. Preserve evidence without configuration dumps, settle that correlated request as typed protocol failure, and keep unrelated pending requests available to the owner disposer. Do not overwrite with whichever reply arrived last or invent a new revision to conceal the conflict.

The native failure union must also distinguish a schema/send rejection from owner disposal. Existing wire `disposed` is historical diagnostic vocabulary; raw shutdown cannot reliably emit it after interrupting command scope, so the proposed producer wire union does not emit that status. A local disposed result names the client's last observation and explicitly does not acknowledge or cancel the request. The producer exhaustion failure reports its existing valid snapshot through the same real commit-gated command, causes no mutation and settles as failed; it follows the same revision comparison policy without fabricating an applied result. These distinctions must be frozen in public signatures/tests before implementation.

## Alternatives and chosen boundary

A Runtime-managed declarative controls/MiniMap view would eliminate host child reattachment and could share Model rendering. It would also replace the current native public mounting boundary and carry a larger renderer/API migration. It is a legitimate later alternative, requiring its own approved source scope. This proposal chooses extension of the already public native mount with one scoped owner and borrowed projections; it retains native UI and keeps accepted graph meaning in its current owner.

A strictly single-flight client could avoid some local reordering by serializing its requests. It would change caller concurrency and still would not order multiple clients, Model replay or arbitrary command completion, and would not settle requests on raw runtime disposal. This proposal chooses producer revision plus correlated drain. The counter is semantic ordering metadata, not a second configuration authority. Neither alternative is implemented or validated here.

## Conformity and deviations

The proposed ownership conforms to the project's core/native adapter/application boundaries and retains existing accepted graph and measurement authority. Exact defaults, computed description, keyboard input and media behavior still require the real reference/native evidence. Source inspection alone establishes no parity.

Native composition lifetime, serializable revisioned ports, local formatter and the distinction between a committed/superseded acknowledgment and paint are proposed intentional adapter differences. They need primary/cold approval and real native tests. Raw `Runtime.EmbedHandle.dispose` remains a public limitation for a ports-only facade; the explicit composed close gives the proposed settlement guarantee. No observer or timeout is represented as a producer acknowledgment.

Implementation, Model migration, coalesced commit output, subscriber/drain behavior, system teardown, archive consumers, captures, focused/full acceptance and all original 189 member cells remain unverified. Deferred option families and accepted 054/058 renderer obligations retain their prior follow-up ownership unchanged. This document creates reviewable contracts only.

# Button Handle recipe trace

## Production paths

- **Vanilla:** The `@flow/vanilla` entry exports `createFlowControlButton`, `mountFlow`, and `createFlowBaseHandle` (`apps/vanilla/src/public.ts:26,78`). The route passes a caller-owned renderer to `mountFlow`; it creates the native button with an app-owned click callback, marks it as excluded from node drag/pan, and returns the renderer lifecycle (`apps/vanilla/src/button-handle-test.ts:14-70`). `mountFlow` renders each declared graph handle as its own focusable button (`apps/vanilla/src/mount-flow.ts:1331-1343`) and owns canvas pointer routing and connection handling (`apps/vanilla/src/mount-flow.ts:1435-1471,5852-5891,6633-6661,7713-7721`).
- **Vue:** `@flow/vue` exports `FlowCanvas`, `FlowControlButton`, and `FlowBaseHandle` (`packages/vue/src/public.ts:1,13,51`). The route's public `nodeTypes` renderer composes the native control and presentation-only handle component in the node visual, with the app owning the action callback (`apps/vue/src/button-handle-test.ts:17-54,76-91`). `FlowCanvas` creates the separate focusable connection button for each decoded handle (`packages/vue/src/flow-canvas.ts:4182-4187`) and handles node pointer input and canvas connection targeting (`packages/vue/src/flow-canvas.ts:2637-2680,3842-3868`).
- **Foldkit:** `@flow/foldkit` exports `createFoldkitControlButton`, `createFoldkitBaseHandle`, and `createProgram` (`packages/foldkit/src/public.ts:2,66,111`). The route gives `createProgram` a node renderer that emits an app-owned placeholder and Base Handle presentation, then replaces the placeholder with the public native button factory after Runtime renders (`apps/foldkit/ui-recipes/button-handle/main.ts:42-65,66-117`). It supplies `['button-node']` as `allowedTargets`; the application constructor forwards that value into the graph model (`packages/foldkit/src/application.ts:2511-2533`), and connection proposal validation rejects target IDs absent from that list (`packages/foldkit/src/graph.ts:796-804`). The Runtime graph creates focusable handle buttons separately from renderer content (`packages/foldkit/src/graph.ts:2916-2930`) and excludes native controls from node dragging (`packages/foldkit/src/graph.ts:2168-2191`).

## Conformity and deviations

- **Conforming within the bounded outcome:** Each host keeps a native button in the node and leaves the canvas/runtime's separate connection handles in place. Enter, Space, and pointer activation call app-owned behavior without moving the node or adding an edge. A pointer-down/move/up gesture starting on the button leaves node position and edge count unchanged, and does not fire another action click. The host interaction tests confirm accepted handle targeting: pointer connection in Vanilla/Vue and keyboard connection in Foldkit.
- **Intentionally different:** The exported composition is host-native: Vanilla uses a DOM node renderer, Vue uses `FlowControlButton`/`FlowBaseHandle` components, and Foldkit uses an `HtmlBuilder` renderer plus app-owned post-render insertion. Foldkit's `createProgram` requires the allowed target IDs to include the intended target; this fixture explicitly supplies `button-node` rather than relying on an empty list.
- **Unverified:** No pinned/current-site comparison was run, so visual, option, and accessibility parity are unverified. A separate implementation-time Foldkit connection-drag probe did not produce an edge despite correct handle hit targets. The final recipe E2E does not claim pointer-connection completion; only its keyboard connection path is verified here. Packed-consumer coverage, screen-reader behavior, and broader focus/lifecycle cases remain unverified. The test boundary is the three local production routes and E2Es cited above.

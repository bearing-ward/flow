# Labeled Handle recipe trace

## Production paths

- **Vanilla:** `createFlowLabeledHandleLabel` and its options are exported through `apps/vanilla/src/public.ts` and implemented in `apps/vanilla/src/ui/labeled-handle.ts:3-19`. The helper creates plain text in a native span with a stable handle-specific ID and side class. The production fixture associates the ID with the existing button and appends the label beside it (`apps/vanilla/src/base-handle-test.ts:86-97`). Its viewport subscription writes inverse zoom to the app root and removes itself on `pagehide` (`apps/vanilla/src/base-handle-test.ts:106-117`); the side-specific transforms consume that value (`apps/vanilla/src/style.css:408-436`).
- **Vue:** `FlowLabeledHandle` is exported from `packages/vue/src/public.ts` and implemented in `packages/vue/src/ui/labeled-handle.ts:8-73`. It renders a native text span and derives inverse transform from public `useFlow().viewport` state (`18,59-71`). On mount it appends its IDREF token without replacing existing descriptions (`22-39`); before unmount it removes only its token and deletes the attribute only when no tokens remain (`41-57`). The node renderer composes it with `FlowBaseHandle` in `apps/vue/src/base-handle-test.ts:33-47`; FlowCanvas owns button focus and connection behavior. The production E2E removes/re-adds the label while the handle remains and checks preservation of an unrelated `existing-help` token (`apps/vue/e2e/labeled-handle-recipe.e2e.ts:21-40`). The test route is `apps/vue/ui-recipes/labeled-handle/index.html`.
- **Foldkit:** `createFoldkitLabeledHandle` and its options are exported from `packages/foldkit/src/public.ts` and implemented in `packages/foldkit/src/ui/labeled-handle.ts:4-22`. The renderer composes labels with existing base handle views in `apps/foldkit/src/main.ts:177-199`. Since Runtime inserts connection buttons asynchronously, the app observes its root for child changes, associates handle IDs through `aria-describedby`, then disconnects that observer on `pagehide` (`apps/foldkit/src/main.ts:241-277`). The app projects inverse zoom from accepted Runtime viewport state (`apps/foldkit/src/main.ts:375-381`), and the label style consumes it (`apps/foldkit/src/playground.css:71-80`). Runtime retains targeting and focus ownership. The test route is `apps/foldkit/ui-recipes/labeled-handle/index.html`.

## Production test paths

- Vanilla `apps/vanilla/e2e/labeled-handle-recipe.e2e.ts` passed 1/1. It checks matching `aria-describedby`, button focus, label text, 12px computed font size, and rendered label height at the initial viewport and three changed wheel-zoom states. Every measured height ratio remained within 5% of 1. The app applies inverse zoom from the public `controller.subscribeViewport` observation and unsubscribes on `pagehide` (`apps/vanilla/src/base-handle-test.ts`).
- Vue `apps/vue/e2e/labeled-handle-recipe.e2e.ts` passed 1/1 with the same association, focus, text, font-size and rendered-height checks across the initial viewport and three changed wheel-zoom states; each ratio remained within 5% of 1. `FlowLabeledHandle` derives its inverse scale from public reactive `useFlow().viewport` state (`packages/vue/src/ui/labeled-handle.ts`).
- Foldkit `apps/foldkit/e2e/labeled-handle-recipe.e2e.ts` passed 1/1. It checks visible label text, description association, focus, 12px font size, and measured rendered height at initial zoom plus 1.25, 0.75, and 1.5 through the public viewport client. Every ratio remained within 5% of 1. The app projects inverse zoom from accepted Runtime viewport state and keeps the DOM association observer lifecycle in the app (`apps/foldkit/src/main.ts`).

## Conformity and deviations

- **Conforming within tested outcomes:** Each host renders a text label, associates it with the existing handle control, preserves the control's focusability, and holds measured label height within a 5% ratio tolerance at the three tested changed zoom states. The Base Handle connection tests passed 1/1 per host after label integration, confirming accepted/rejected targeting remained unchanged for those fixtures.
- **Intentionally different:** Vanilla exposes an imperative DOM helper, Vue exposes a component, and Foldkit exposes an HtmlBuilder view. Their host-owned lifecycle surfaces differ: public controller observation, reactive public viewport state, and accepted Runtime state respectively drive the inverse visual scale. Foldkit performs DOM association in app lifecycle code because Runtime inserts buttons asynchronously. These APIs do not add label text to persisted graph data.
- **Unverified:** Zoom values outside the tested states, other side placements, and visual behavior against the reference remain open. The exact implementation boundary is the three focused local recipe E2Es above; upstream comparison remains unverified, so no parity claim is made.

# Public viewport operations contract

## Production path

All adapters share the serializable viewport types and pure geometry in `packages/core/src/domain/flow-viewport-operation.schema.ts:6-51,53-73,75-101,103-109,143-193`. The bounds function rejects non-finite or zero-area panes/bounds, applies pinned numeric, px/percent string, or per-side padding, clamps zoom to the configured limits, centers the bounds, and corrects sides that fall short of requested padding. `packages/core/src/domain/flow-fit-view.ts:15-32,41-79` builds graph bounds from visible document nodes and measured dimensions, with a default fallback of 150×44; empty selection or unavailable pane preserves the current viewport. Pure interpolation is shared; each browser adapter schedules frames.

Vanilla exposes the controller contract at `apps/vanilla/src/mount-flow.ts:551-606` and public facade at `apps/vanilla/src/mount-flow.ts:648-695`. The mounted controller's real DOM entry at `apps/vanilla/src/mount-flow.ts:6853-6870` reads accepted viewport/zoom/readiness and converts between client coordinates and flow coordinates by subtracting/adding the canvas `getBoundingClientRect()` origin. Its operation dispatcher and API entry points are at `apps/vanilla/src/mount-flow.ts:6541-6703,6791-6898`; `fitView` uses document selection, measurements, fallback dimensions, and pane size. External owner updates supersede pending animation at `apps/vanilla/src/mount-flow.ts:7077-7083`. The application facade forwards these methods at `apps/vanilla/src/mount-flow.ts:7190-7255,7342-7346`.

Vue's public `FlowEditor` methods and return types are declared in `packages/vue/src/use-flow.ts:98-126`; the composable returns those methods at `packages/vue/src/use-flow.ts:260-280`. The canvas owns DOM measurements and operation lifecycle in `packages/vue/src/flow-canvas.ts:857-933,936-1015,1018-1153`. Coordinate conversions use the canvas client-rect origin. Uncontrolled operations update the accepted viewport and return a terminal result; controlled operations emit a proposal and return `proposed`, without claiming owner acknowledgement. A replacement or owner update settles the active request as superseded, and canvas teardown settles it as disposed (`packages/vue/src/flow-canvas.ts:882-933,1034-1081,2078`).

Foldkit transports serializable viewport requests/results across its application boundary (`packages/foldkit/src/application.ts:85-124,180-185,231-250`). Its request handler computes bounds and coordinate conversions from host-fed pane dimensions and current graph state (`packages/foldkit/src/application.ts:582-662`), then returns request-ID-bearing terminal responses and distinguishes controlled proposals from accepted updates (`packages/foldkit/src/application.ts:665-697`). Animation progress is driven by the host frame subscription and shared interpolation; graph state remains the accepted viewport (`packages/foldkit/src/graph.ts:298-320,1109-1124`).

## Async and ownership contract

Viewport mutations resolve to a terminal `ViewportOperationResult` with a monotonically increasing request ID and status. `accepted` means the uncontrolled adapter committed the resulting viewport; controlled adapters resolve `proposed` immediately because only the owner can acknowledge by supplying a new viewport. `unchanged`, `unavailable`, `superseded`, `disposed`, and `rejected` describe non-acceptance or terminal interruption. Animation duration defaults to zero; nonzero duration and linear/ease-in-out easing are adapter-scheduled. Reduced-motion preference forces immediate completion. A newer request or external owner update takes priority over an in-flight animation and settles it as superseded; disposal settles it as disposed. No promise waits indefinitely for an owner acknowledgement.

The historical Vanilla `fitView` API returned a synchronous boolean (`apps/vanilla/src/mount-flow.ts:510-527` at the pre-change baseline). The public operation now returns a promise of the explicit terminal result so animated completion, proposal-only control, replacement, and disposal have defined meanings. Existing fire-and-forget UI call sites remain valid; callers that relied on the boolean must migrate to inspect the result status. `viewportInitialized` is a readiness query, not a promise and not proof that every node is measured.

Client/screen conversions account for the host element's client-rect offset and document scrolling through browser client coordinates. CSS-transformed/scaled canvas hosts are not supported: `getBoundingClientRect()` returns transformed dimensions/origin while the pane math uses layout pixels. The tests do not claim transformed-host parity. Host movement observations (`start`, `change`, `end`) remain adapter-local; accepted state subscriptions continue to report accepted-state changes separately.

## Extent boundary

`PanExtentSchema` models a finite Flow-space rectangle and `constrainViewportToExtent` keeps the visible pane rectangle within it (`packages/core/src/domain/flow-pan-extent.schema.ts:5-31,37-63`). The chosen policy preserves Vanilla's existing constraint on programmatic viewport operations (`apps/vanilla/src/mount-flow.ts:1042-1053,6536-6544`). Vue and Foldkit do not gain a new pan-extent option; their programmatic targets remain unconstrained by a Flow-space rectangle. This decision preserves the existing host boundary and does not claim cross-host extent parity.

## Conformity and deviations

- **Conforming:** pane-local fit math, min/max zoom, centered bounds, upstream numeric, string, and per-side padding, set/zoom/center/fit operations, and screen-coordinate origin handling match the pinned upstream behavior for captured cases. The shared reference fixture includes asymmetric padding and actual DOM transform checks.
- **Intentionally different:** Flow returns explicit terminal results and settles interrupted/disposed operations. The pinned upstream transition helper can leave an interrupted animation promise pending; Flow's bounded lifecycle contract avoids hanging callers. Controlled Flow operations return `proposed` rather than reporting acceptance before owner acknowledgement.
- **Intentionally different:** Vanilla's existing pan extent constrains programmatic viewport targets, while pinned xyflow's `fitViewport` uses the unconstrained setter. Vue and Foldkit do not currently expose this Flow-specific constraint, so extent behavior is not cross-host equivalent.
- **Intentionally different:** Plan 144 replaces the old numeric pane-fraction and numeric-side pixel policy with pinned xyflow semantics. Malformed units and non-finite values are rejected at Flow's decode boundary rather than logged and replaced with zero. Empty, zero-area, or unmeasured fit inputs produce a stable unchanged/unavailable result rather than inventing a target. This preserves deterministic viewport ownership and avoids division by zero.
- **Unverified:** Vanilla extent enforcement through public viewport operations, Vue/Foldkit extent behavior, pinned upstream extent behavior under the capture fixture, CSS-transformed/scaled canvas coordinate conversion, browser-specific reduced-motion behavior outside the exercised browser, and hosted/production delivery. The chosen Vue/Foldkit gaps are policy decisions, not tested parity. Conformity claims are bounded to the pinned SHA and named browser/core test boundaries; the dated website catalog is a separate moving contract.

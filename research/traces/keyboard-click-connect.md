# Keyboard access to click connections

Status: traced against pinned xyflow commit `0a1f9575b25679f2880175de8d3eae21aedde921`. Reference paths below are relative to `research/artifacts/xyflow/0a1f9575b25679f2880175de8d3eae21aedde921/`.

## React production path

The public `connectOnClick` prop promises click or tap activation of a source handle followed by a target handle; it does not describe keyboard activation (`packages/react/src/types/component-props.ts:588`). `Handle` accepts general HTML `div` attributes, so a custom handle caller can pass accessibility attributes (`packages/react/src/components/Handle/index.tsx:36`). By default, it renders a `div` with `onClick` only when `connectOnClick` is enabled. That element has no built-in role, `tabIndex`, or key handler in this component (`packages/react/src/components/Handle/index.tsx:239`, `packages/react/src/components/Handle/index.tsx:273`). The default handle therefore does not establish a keyboard focus and activation path in this source.

The click handler reads `connectionClickStartHandle` from the store (`packages/react/src/components/Handle/index.tsx:185`). Its first activation saves the source handle; its second validates the clicked handle through `XYHandle.isValid`, publishes a connection on success, calls the end callback, and clears the saved source even on an invalid second activation (`packages/react/src/components/Handle/index.tsx:202`, `packages/react/src/components/Handle/index.tsx:210`, `packages/react/src/components/Handle/index.tsx:227`, `packages/react/src/components/Handle/index.tsx:236`). The selector applies `clickconnecting` to the first handle and `connectionindicator` to possible endpoints (`packages/react/src/components/Handle/index.tsx:77`, `packages/react/src/components/Handle/index.tsx:255`). These state and DOM effects can be reached by a programmatic click or by custom keyboard activation supplied by a caller, but the default component does not wire such activation.

## Svelte production path

The public `clickConnect` prop enables handle clicks (`packages/svelte/src/lib/container/SvelteFlow/types.ts:428`). `Handle` attaches `onclick` when that prop is enabled and includes a no-op `onkeypress`, `role="button"`, an accessible label, and `tabindex="-1"` (`packages/svelte/src/lib/components/Handle/Handle.svelte:223`). The default handle is not in sequential Tab order. The rest props are spread after these attributes, so a caller may supply its own attributes (`packages/svelte/src/lib/components/Handle/Handle.svelte:231`); this trace does not establish how a custom keyboard handler interacts with the no-op handler.

On first click, Svelte stores the source handle (`packages/svelte/src/lib/components/Handle/Handle.svelte:145`). On the second, it validates and may add an edge, then clears the saved source (`packages/svelte/src/lib/components/Handle/Handle.svelte:156`, `packages/svelte/src/lib/components/Handle/Handle.svelte:177`, `packages/svelte/src/lib/components/Handle/Handle.svelte:191`). Its `connectionindicator` class exposes pending endpoints (`packages/svelte/src/lib/components/Handle/Handle.svelte:220`). No key handler in the traced handle component calls this click path.

## Reference test path

The pinned shared Playwright connection test uses pointer hover, mouse down, pointer movement, and mouse up; it asserts the resulting edge (`tests/playwright/e2e/nodes.spec.ts:199`). The adjacent negative cases also use pointer dragging (`tests/playwright/e2e/nodes.spec.ts:224`, `tests/playwright/e2e/nodes.spec.ts:252`). The pinned suite has no assertion that Tab reaches a handle or that Enter or Space starts or completes a click connection. The pointer tests cannot establish keyboard behavior.

## Flow production path

The vanilla renderer creates each handle as a native `button` with `type="button"` and an accessible name (`apps/vanilla/src/mount-flow.ts:252`). A native button can receive keyboard focus and dispatch click on Enter or Space. The canvas listens for bubbled clicks and routes handle clicks through `onHandleClick` when `connectOnClick` is enabled (`apps/vanilla/src/mount-flow.ts:2717`, `apps/vanilla/src/mount-flow.ts:2779`, `apps/vanilla/src/mount-flow.ts:3150`). That handler starts or cancels on a source handle and attempts a connection on a target handle (`apps/vanilla/src/mount-flow.ts:2743`, `apps/vanilla/src/mount-flow.ts:2759`). `beginClickConnection` keeps focus on a source button already focused by keyboard activation; a pointer start focuses the canvas (`apps/vanilla/src/mount-flow.ts:2540`, `apps/vanilla/src/mount-flow.ts:2551`). The canvas keydown listener cancels a pending connection on Escape (`apps/vanilla/src/mount-flow.ts:2888`, `apps/vanilla/src/mount-flow.ts:3154`).

The host appends a persistent, visually hidden status element with `role="status"`, `aria-live="polite"`, and `aria-atomic="true"` (`apps/vanilla/src/mount-flow.ts:289`, `apps/vanilla/src/mount-flow.ts:3162`, `apps/vanilla/src/style.css:185`). It announces the source and next action when a click connection begins (`apps/vanilla/src/mount-flow.ts:2545`). It announces cancellation, including a source-removal reason, and returns focus to the source or canvas if the source is absent (`apps/vanilla/src/mount-flow.ts:785`). Target activation clears pending state, validates the candidate, announces rejection or completion, and returns focus to the source handle (`apps/vanilla/src/mount-flow.ts:2498`, `apps/vanilla/src/mount-flow.ts:2507`, `apps/vanilla/src/mount-flow.ts:2517`, `apps/vanilla/src/mount-flow.ts:2759`). A validator exception is converted to rejection without exposing exception details in the status (`apps/vanilla/src/mount-flow.ts:2455`, `apps/vanilla/src/mount-flow.ts:2507`).

## Flow decision for pending-connection accessibility

Flow uses the source handle as the focus return point after cancellation, completion, or rejection (`apps/vanilla/src/mount-flow.ts:799`, `apps/vanilla/src/mount-flow.ts:2763`). This gives a repeatable starting point for another connection. Source removal instead sends focus to the canvas (`apps/vanilla/src/mount-flow.ts:801`), and host destruction emits no status message (`apps/vanilla/src/mount-flow.ts:792`). The status changes at connection start and end boundaries, not during pointer movement (`apps/vanilla/src/mount-flow.ts:296`, `apps/vanilla/src/mount-flow.ts:785`, `apps/vanilla/src/mount-flow.ts:2507`, `apps/vanilla/src/mount-flow.ts:2547`). These are Flow host choices; the pinned reference provides no keyboard or live-region requirement.

The browser test can establish status text, DOM focus, and native button activation. It cannot establish that a screen reader spoke the message. The current follow-up test does not cover cancellation after source removal, a rejected target, a throwing validator, a target reached solely by keyboard, or entry into the graph from outside (`apps/vanilla/e2e/flow-followups.e2e.ts:265`). Those remain separate test boundaries.

## Conformity and deviations

- **Conforming:** Both Flow and the reference use a saved first handle, second-handle validation, and a visible pending state. Flow's browser tests cover pointer clicks and keyboard Enter, Tab, Space, and Escape on its native handles; the pinned reference suite covers pointer dragging.
- **Intentionally different:** Flow renders native focusable buttons for handles and a live status region. React's default handle is a `div` without built-in keyboard attributes; Svelte's handle has `tabindex="-1"`. Flow returns focus to the source after a click connection ends and allows Escape cancellation. These are Flow host accessibility and interaction choices, not evidence of upstream keyboard parity.
- **Unverified:** The pinned tests do not establish keyboard click-to-connect behavior. Flow's test starts with programmatic source focus and verifies the Tab route to one target; the follow-up test verifies status DOM text and focus for start, Escape, pane click, and completion. It does not establish entry into the graph from outside, other DOM orders, actual screen reader speech, custom handle markup, source-removal focus, or rejection announcements. The tested boundary is the default vanilla handles in one graph.

# Deterministic offline workflow runner

Plan 172 implements Unit 4 of [Plan 168](../../plans/168-workflow-delivery.md) and its adopted D3/D4 decisions. The [template audit](workflow-templates-audit-2026-10-26.md) remains the upstream evidence boundary. This unit adds original offline execution without importing template source or changing `research/artifacts/`.

## Public execution contract

The public entry is `startWorkflowRun` at `packages/workflow/src/workflow-runner.ts:166`. It accepts a fresh accepted document/revision, expected revision, unknown run ID, event subscriber and optional Effect evaluator. `prepareWorkflowExecution` revalidates the revision and current graph at `packages/workflow/src/workflow-preparation.ts:354`. The runner retains a detached, recursively frozen `WorkflowRunRequest`; later document edits cannot change its configuration or geometry. Schema-derived values, node events, run events, outputs and projection state live in `packages/workflow/src/workflow-execution.schema.ts:13` and `packages/workflow/src/workflow-execution.schema.ts:64`.

Preparation failures remain typed Effect failures before event publication. The session has `request`, `cancel` and `await`; its fiber belongs to the caller's Effect scope. Runtime evaluator failures become node/run failure events, and interruption marks unfinished nodes cancelled through `packages/workflow/src/workflow-runner.ts:335`. `await` completes after success or runtime failure and is interrupted on cancellation. The evaluator boundary validates output encodings, semantic roles and value types before retaining results. Unexpected defects yield the redacted `evaluator-defect` code.

`evaluateOfflineWorkflowNode` starts at `packages/workflow/src/workflow-runner.ts:47`. Initial, transform, branch, join and output evaluation is deterministic. Text Input and Workflow Trigger are also local. AI generation fails with `unsupported-kind`; provider execution remains Unit 6. Output roles are semantic names, and the terminal output node publishes `result`. Neither local evaluator nor runner owns network access, credentials or persistence.

The preparation plan selects one ready node at a time by stable node ID. The runner uses its ordered steps and physical-to-semantic port mapping. Each input comes only from a succeeded predecessor's emitted source role. An unselected branch role has no value, so its downstream required inputs skip. Joins wait for every predecessor's settlement, consume active inputs in source-node-ID/edge-ID order and skip if all inputs are inactive. Failure skips pending nodes and stops evaluation. Cancellation preserves already completed results and marks all unfinished nodes cancelled.

`reduceWorkflowRunEvent` at `packages/workflow/src/workflow-run-state.ts:32` checks run ID, snapshot revision, current accepted revision, terminal session state and node transitions. A late event cannot replace a new run or an edited document's run state. The owner selects identity before subscription. Events cannot create a new session.

## Production browser paths

Every host's `/workflow/` route mounts the real Run and Cancel controls through `apps/shared/workflow/demo.ts:518` and `apps/shared/workflow/run-controls.ts:4`. Run reads a fresh snapshot and the displayed expected revision, then calls the app-owned session at `apps/shared/workflow/run-owner.ts:30`. That owner allocates a run ID, opens an Effect scope, subscribes through the shared reducer and paces local evaluation with an interruptible 200 millisecond delay. The package evaluator has no demo delay. Cancel closes the scope and waits for finalizers. Document edits invalidate the current generation, clear displayed results and close the previous scope.

Vanilla composes the public controller at `apps/vanilla/workflow/main.ts:76`. The model's semantic revision and `subscribeState` path at `apps/vanilla/workflow/main.ts:127` invalidate the app run owner. Custom renderer subscriptions use public `createFlowStatusIndicator`/`updateFlowStatusIndicator` at `apps/vanilla/workflow/main.ts:34`. Controller destruction and pagehide remove subscriptions and close the run scope.

Vue owns the same state in component-scoped `shallowRef` at `apps/vue/workflow/main.ts:40`. `FlowProvider`, `FlowCanvas` and `useFlow` still own accepted graph state. Public accepted-state subscription at `apps/vue/workflow/main.ts:97` advances semantic revision and invalidates the run. The node renderer reads the ref and uses the existing `StatusIndicator` plus literal state text. `onScopeDispose` closes the run and releases controls and subscriptions at `apps/vue/workflow/main.ts:116`.

Foldkit's app model adds a transient `run` field at `apps/foldkit/workflow/main.ts:50`. Event reduction updates that model and sends public `HostAction.RefreshRenderers` at `apps/foldkit/workflow/main.ts:124`; no node data edit occurs. The node renderer uses `createFoldkitStatusIndicator`. Accepted-state port decoding at `apps/foldkit/workflow/main.ts:174` updates semantic revision and invalidates runs. App disposal at `apps/foldkit/workflow/main.ts:158` closes the scope before disposing clients and runtime. The generic renderer lookup now honors a registered `default` renderer when node type is omitted at `packages/foldkit/src/graph.ts:7957`, as Vanilla and Vue already do.

All hosts retain the existing public edit, viewport, clipboard and history APIs. `workflowDocumentChanged` uses core's history projection at `apps/shared/workflow/validation.ts:13`. Semantic configuration, topology, presentation edits, undo, redo, paste and incoming accepted replacements invalidate a run. Selection, measurements and viewport changes preserve it. The run owner has no edit, history, persistence or room-write capability. This is the D4 boundary.

## Geometry, DOM effects and rendered output

Execution reads immutable workflow configuration and port mapping; it never writes positions, handles, routes, parents, shapes, trees, bundles or rotation. Canvas edits still use core geometry at `packages/core/src/domain/flow-edge-geometry.ts:176`, and physical handles follow the existing host renderers. Session updates change only app state, renderer presentation, accessible status text and read-only output. Queued, running, cancelled and skipped use the waiting status indicator with explicit state labels. Succeeded uses ready; failed uses error.

The shared controls render transient JSON separately from accepted graph JSON. The selected configuration panel reads node outputs through `apps/shared/workflow/demo.ts:432`. Run results never enter document update calls. Foldkit renderer refresh changes render state without a document transaction, so it adds no history or room change. React and Svelte workflow adapters are outside this unit; no new framework integration is inferred from the shared package.

## Test paths and acceptance boundaries

Package acceptance starts through public exports at `packages/workflow/src/workflow-runner.test.ts:72`. The in-memory evaluator and Effect TestClock assert literal event order, true/false branches, inactive chain skipping, active-input join values, deterministic simultaneous-ready ordering, runtime failure stops, malformed outputs, redacted defects, cancellation, rerun, immutable snapshots, pre-run revision rejection and scope finalization. The stale-event test checks old IDs, old revisions, edited accepted revisions and terminal sessions. The D4 test compares saved/history/clipboard/room projections before and after a real run at `packages/workflow/src/workflow-runner.test.ts:737`.

Browser entry files are each host's `workflow-runner.e2e.ts`. Their shared acceptance starts at `apps/shared/workflow/run-acceptance.ts:27` and drives the real `/workflow/` controls. It observes running and terminal rendered status, exact HELLO/CHANGED output, typed unsupported-AI failure, visible invalid-run reasons, cancellation and rerun, accepted configuration invalidation and undo/redo. A combined fixture retains groups, trees, shapes, rotation, manual routes and bundles through execution and clipboard paste. Unexpected HTTP requests are blocked and fail acceptance, and page errors fail acceptance.

The disposal test instruments browser timers before application boot and verifies that an active local evaluation exists, unmounts through the real Dispose control, then checks timer release, removed DOM and no newly scheduled work after controlled time advances. Foldkit also schedules lifecycle timers at the same delay. The test requires active timers before disposal and requires all of them to be released, without assuming there is exactly one. This browser probe is separate from the package TestClock/finalizer proof.

The real local WebSocket test at `packages/collaboration-yjs/src/public.test.ts:204` runs the shared runner on a room snapshot, requires queued/running/succeeded events, compares both peers' unchanged documents, then exercises configuration replication and room undo. Packed consumers execute the public runner beside each adapter archive at `tests/consumer/workflow-contracts.runtime.ts:99`. Core-only packed acceptance continues to prove that generic Flow use needs no workflow package.

## Observability and verification scope

The central registry adds `FlowSpan.workflowRun`, `FlowSpan.workflowNode`, `FlowAttribute.workflowRunId` and `FlowAttribute.workflowRevision` at `packages/core/src/telemetry/flow-telemetry.ts:33` and `packages/core/src/telemetry/flow-telemetry.ts:77`. Run and node boundaries carry identifiers; lifecycle and failure logs omit configuration, prompts, output, credentials and raw defect content. Decode/preparation retains existing document spans. Pointer moves do not log. Applications own OTLP export and shutdown; this work claims no collector delivery.

Architecture fixtures reject runner subpath and implementation imports from core and all generic adapters in `scripts/check-architecture.ts`. No dependency is added. Verification configuration only appends Plan 172 and the three runner browser files, retaining all previous checks and files.

The required final command is `scripts/with-flow-browser-lock.sh bun run verify --check reference-host`. Each standalone browser command acquires its own lock and uses one worker. Test runners own and stop their own child processes. No process is killed by name or port. Final results are recorded in the implementation handoff. This is focused verification with the retained selected scope, not `verify:full` or complete template acceptance.

## Conformity and deviations

- Conforming to adopted Flow Unit 4 and D4: scoped Effect lifetime, immutable accepted snapshots, schema-derived events, sequential stable scheduling, branch skipping, joins over settled active inputs, cancellation, typed failure stops, stale-event rejection and transient app ownership. The package, three-host browser, real transport and packed-consumer tests define the acceptance boundary.
- Intentionally different from upstream behavior that remains unverified: deterministic local simulation, explicit D3 branch/join policy, app-owned run sessions and 200 millisecond demo pacing. These choices follow the adopted maintainer decisions. Generate Text/Image remain explicit unsupported runtime failures until Unit 6 supplies the offline provider.
- Unverified: upstream template runtime internals, subscriptions, failure/cancellation semantics, React/Svelte workflow hosts, external providers, durable jobs, run resume and collector-side OTLP delivery. No catalog promotion, full template parity or full-profile acceptance is claimed.

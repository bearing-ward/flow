## Contracts and ownership

The package public entry is `packages/workflow/src/public.ts:54`. `WorkflowKindSchema` and the `workflowKinds` tuple enumerate the nine adopted kinds at `packages/workflow/src/workflow-edit.ts:26`. `WorkflowEditSchema` derives add, append, configure and delete commands at `packages/workflow/src/workflow-edit.ts:62`. IDs come from an explicit caller-owned `WorkflowIds.allocate` capability at `packages/workflow/src/workflow-edit.ts:43`. No core or reusable adapter imports workflow. Architecture checks reject static, type-only and dynamic imports and manifest dependencies for all four library owners. Browser code stays in the three app entries and shared app controls.

`createWorkflowNode` at `packages/workflow/src/workflow-edit.ts:192` supplies typed default configuration, fresh port bindings, declared handles, renderer type and authored geometry. `prepareWorkflowEdit` at `packages/workflow/src/workflow-edit.ts:402` is the unknown-command boundary. It validates the current document, resolves a transaction, reuses core `prepareFlowEdit`, validates the proposed workflow, and returns one transaction. Preparation does not mutate the document or accept a history transition. The existing host owner accepts that transaction. All schema and integrity checks occur before the host edit.

Append finds compatible ports, retains the original edge ID/source handle and changes its target. It adds one downstream edge with a fresh ID. Thus a true/false branch keeps its incoming role and bundle references to the original edge remain valid. Configuration edits retain accepted ports and opaque metadata and cannot change kind. A locked Text Input rejects text changes, including a simultaneous unlock-and-change. Unlock first, then edit. This does not lock geometry. Deletion reuses core element deletion and bundle pruning, then reconnects compatible predecessor/successor pairs with incoming source handles. Duplicate pairs collapse. Multiplicity or cycle violations reject the entire edit rather than accepting a partial deletion.

Workflow meaning stays in `data.workflow`, independently of groups, tree metadata, shape renderer data, rotation, manual edge routes and bundles. Existing clipboard reference maps own node, edge, parent and physical handle remapping; `workflowClipboardExtension` at `packages/workflow/src/workflow-document.ts:105` remaps only semantic port bindings. Opaque JSON is not searched for ID strings. Neither transient execution nor credentials enter the document.

## Conformity and deviations

- **Conforming to the adopted Flow Unit 2 contract:** nine-kind factories/palettes, public host ownership, viewport-aware insertion, atomic port-preserving append, typed configuration, Text Input lock/unlock, delete/reconnect, history and workflow clipboard remapping have package and real-host acceptance tests. Extension and local room tests establish the stated interoperability boundary.
- **Intentionally different:** small typed panels, the explicit lock rule and transaction semantics are adopted Flow decisions. The app's edge insert action currently inserts a transform, with package APIs supporting compatible kinds. Model IDs remain plain local configuration, and the output area is read-only without execution. No external AI service, key UI or provider dependency is added. These choices follow the adopted unit ordering and deterministic-offline boundary.
- **Unverified against upstream:** upstream edge-plus gesture details, Text Input locking semantics, private licensed template implementation, provider model/settings parity and runtime subscriptions remain unverified. No upstream edge-plus gesture was captured in this unit, so no gesture parity claim is made. Functional tests prove Flow behavior only. Both templates retain their prior catalog classification pending later integration and locked full-profile verification.

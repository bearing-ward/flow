# Node connection observer trace

This trace compares the pinned React `useNodeConnections` behavior with Flow's host-native observers. `FlowNodeConnection[]` remains the shared projection; this is not a claim that Flow returns React's `NodeConnection[]` or internal `HandleConnection[]` payloads.

## Pinned React path

`useNodeConnections` chooses the explicit `id` or falls back to `useNodeId()` and errors without either (`research/artifacts/xyflow/0a1f9575b25679f2880175de8d3eae21aedde921/packages/react/src/hooks/useNodeConnections.ts:43-49`). It selects a node/direction/handle-specific connection map from the React store (`research/artifacts/xyflow/0a1f9575b25679f2880175de8d3eae21aedde921/packages/react/src/hooks/useNodeConnections.ts:51-59`). Its effect skips callbacks until it has a previous map; on later map changes it invokes disconnect before connect and stores the current map (`research/artifacts/xyflow/0a1f9575b25679f2880175de8d3eae21aedde921/packages/react/src/hooks/useNodeConnections.ts:61-70`). It returns an array of the selected map values (`research/artifacts/xyflow/0a1f9575b25679f2880175de8d3eae21aedde921/packages/react/src/hooks/useNodeConnections.ts:72`).

## Flow shared projection and delta

Core defines `FlowNodeConnection` as edge ID, endpoints, and optional source/target handle IDs (`packages/core/src/domain/flow-selectors.ts:15-21`). `selectNodeConnections` filters a document's edges by node, optional direction, and optional handle; with no direction it includes edges touching either endpoint (`packages/core/src/domain/flow-selectors.ts:146-185`). `diffNodeConnections` keys by edge ID and compares endpoints and handles; removed or changed entries appear in `disconnected`, while added or changed entries appear in `connected` (`packages/core/src/domain/flow-selectors.ts:29-66`). Each adapter invokes disconnect before connect when each delta is nonempty.

The helper is deliberately projection-specific. It does not convert Flow connections to React connection payloads or normalize host options into React's `id`, `handleType`, and `HandleConnection` types. The core regression exercises edge addition/removal plus a same-ID endpoint change (`packages/core/src/domain/flow-selectors.test.ts:55-92`).

## Vanilla production path

The `FlowController` interface exposes an explicit-node-ID `observeNodeConnections` observer alongside its point-in-time getter (`apps/vanilla/src/mount-flow.ts:876-896`). The implementation snapshots the initial projection silently, subscribes to controller state, selects connections from each `current.document`, computes the delta, invokes callbacks in disconnect/connect order, and returns an idempotent unsubscriber (`apps/vanilla/src/mount-flow.ts:8479-8519`). Controller state publication installs the new accepted snapshot before it notifies state listeners, and skips schema-equivalent snapshots (`apps/vanilla/src/mount-flow.ts:1963-2000`). Observer callbacks are invoked independently through the existing boundary callback reporter, so a throwing disconnect is reported through `onError` and telemetry without preventing connect delivery (`apps/vanilla/src/mount-flow.ts:1834-1872,8438-8457`). The JavaScript facade forwards the observer (`apps/vanilla/src/mount-flow.ts:9059-9053`).

The mounted controller E2E verifies silent controlled proposals/rejection, accepted add, same-ID reconnect, removal, unsubscription, and two-controller isolation (`apps/vanilla/e2e/public-state.e2e.ts:1035-1128`).

## Vue production path

`FlowNodeIdKey` provides node context to each custom node renderer (`packages/vue/src/flow-canvas.ts:424-437`). `useNodeConnections` accepts explicit `nodeId` or that context, returns `useFlow().getNodeConnections(...)` as a computed value, and watches it without immediate delivery; changed projections call disconnect before connect (`packages/vue/src/use-flow.ts:875-911`). The computed getter reads the editor's `snapshot.value.document` (`packages/vue/src/use-flow.ts:387-405`). FlowCanvas emits `FlowStateChange` notifications only when its accepted snapshot changes (`packages/vue/src/flow-canvas.ts:809-932`), so a controlled proposal does not trigger the connection watcher until the owner updates the controlled document.

The two-canvas E2E exercises node-context fallback, silent initial state, controlled proposal/reject/accept, add, reconnect, removal, and isolation when both canvases use the same node and edge IDs (`apps/vue/e2e/node-connections.e2e.ts:21-156`; fixture `apps/vue/src/node-connections-test.ts:28-190`). A callback exception is captured per callback; Vue still attempts connect delivery for the same delta and then rethrows the failure through the watcher so the configured Vue app error handler receives it (`packages/vue/src/use-flow.ts:898-930`). Vue's returned computed projection is a host-native reactive value; the observer does not claim React's effect timing or callback identity behavior.

## Foldkit production path

The Foldkit observer is exported by the `@flow/foldkit` package root (`packages/foldkit/src/public.ts:58-60`); it requires an explicit node ID and accepts callback functions in host composition (`packages/foldkit/src/observers.ts:34-69,71-95`). It subscribes to the one Runtime's accepted-state port, decodes each message as `FlowSnapshot`, projects that snapshot, and dispatches the delta in disconnect/connect order (`packages/foldkit/src/observers.ts:135-195`). Each observer starts with the current Runtime projection and therefore has no mount callback (`packages/foldkit/src/observers.ts:209-222`). Runtime disposal calls `observers.dispose()` (`apps/foldkit/src/main.ts:500-510`); disposal unsubscribes the accepted-state source and clears connection observers (`packages/foldkit/src/observers.ts:209-222`). Callbacks stay host-local and are never sent over the serializable Runtime ports. If one callback throws, Foldkit attempts the other callback for the same delta and reports each failure through an Effect error log (`packages/foldkit/src/observers.ts:159-195`).

The mounted Runtime E2E verifies controlled proposal/rejection, accepted add, reconnect, removal, disposal, and isolation between controlled and uncontrolled Runtime instances (`apps/foldkit/e2e/public-state.e2e.ts:318-431`). The test harness binds callbacks to `createFoldkitObservers`, not a wire-level callback payload (`apps/foldkit/e2e/test-harness.ts:1936-1988`).

## Conformity and deviations

- **Conforming:** all hosts skip initial callbacks, observe accepted state, emit disconnect before connect for a changed projection, remain silent for unacknowledged controlled proposals, stop after disposal, and attempt connect delivery even when the same-delta disconnect callback throws. The focused observer E2Es exercise each host error boundary. The three mounted host E2Es cover these boundaries; see the test locations above.
- **Intentionally different:** Flow exposes `nodeId`/`type`/`handleId` (Vue allows omitted `nodeId` inside its custom-node context), while React names these `id`/`handleType`/`handleId`. Vanilla and Foldkit are explicit-ID controller/Runtime observers; Vue returns a computed Flow projection. Flow payloads are `FlowNodeConnection[]`, not React's `NodeConnection[]` or system `HandleConnection[]`.
- **Unverified:** React hook rerender/effect scheduling, callback identity replacement behavior, full upstream option-union parity, and live pinned-runtime output comparison were not tested. The Foldkit observer is package-public through `@flow/foldkit`; this workspace test does not prove packed-consumer behavior. Callback-failure regressions exercise each host error boundary; they do not establish full Vue component error-capture ordering beyond the configured app error handler. The test boundary is each host's mounted production adapter/Runtime path, plus one pure core delta test; no reference React runtime was run.

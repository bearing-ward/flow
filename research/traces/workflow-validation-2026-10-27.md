# Workflow validation and execution preparation

Plan 171 implements Unit 3 of [Plan 168](../../plans/168-workflow-delivery.md), including the maintainer decisions recorded on 2026-10-26. The public contract is original Flow behavior. The [template audit](workflow-templates-audit-2026-10-26.md) records the bounded upstream evidence. Imported artifacts remain unchanged.

## Public entry points and contracts

`workflowValidationReport` accepts a decoded `WorkflowDocument` and returns the schema-derived `WorkflowValidationReport` at `packages/workflow/src/workflow-preparation.ts:101`. The report combines structural issues with missing required inputs, invalid semantic settings, unreachable executable nodes and an empty executable graph. Reports sort their issues and reachable IDs. Existing `workflowIssues` remains the editable integrity policy at `packages/workflow/src/workflow-validation.ts:262`; incomplete graphs remain editable.

`WorkflowExecutionPlanSchema` defines revision, detached document, explicit branch/join policy and steps at `packages/workflow/src/workflow-preparation.ts:193`. Steps preserve physical port IDs, semantic source/target roles, required ports, dependency edge IDs and outputs. `createWorkflowExecutionPlan` returns an invalid report or a ready plan at `packages/workflow/src/workflow-preparation.ts:232`. At every step it selects the smallest ready node ID, independently of document array order. Joins wait for all predecessor outcomes to settle, consume active outputs, and skip when none are active. Other nodes skip when a required input is inactive. Optional inactive inputs use configured fallback values. There is no evaluator or scheduler in Unit 3.

`prepareWorkflowExecution` accepts a fresh owner snapshot and expected revision at `packages/workflow/src/workflow-preparation.ts:354`. It rejects stale revisions, decodes the current document through `packages/workflow/src/workflow-document.ts:49`, recomputes readiness, and returns a detached plan. Encoding errors, invalid executable graphs, revision mismatches and future runtime node failures remain separate contracts. `prepareWorkflowConnection` decodes an edge and prepares a fully validated transaction at `packages/workflow/src/workflow-edit.ts:434`. The core transaction entry remains `packages/core/src/domain/flow-edit.ts:247`.

Required base inputs are transform, branch, join and output `input` ports. AI generation requires a trigger and either a connected prompt or nonblank inline prompt. System text is optional. Entries are initial, Text Input and Workflow Trigger. Presentation membership does not create execution dependencies. Blank model IDs and empty `contains` comparisons are semantic setting issues; malformed typed settings remain document decode failures. Provider capability checks belong to Unit 6.

## Conformity and deviations

- Conforming to the adopted Flow plan: finite DAG validation, explicit branch roles, active-input joins, stable sequential plan order, typed errors, revision revalidation, accessible reports, immutable-source preservation and three-host application ownership. The named unit/browser/transport/packed-consumer tests define this boundary.
- Intentionally different from unverified upstream semantics: Flow specifies reachability, required prompts/triggers, skipped-branch propagation, join settlement and semantic settings explicitly. These choices implement the maintainer's adopted D3 decision. Unit 3 prepares plans and labels execution as unavailable until Unit 4. Canvas gestures create data edges; typed controls cover both data and trigger connections.
- Unverified: upstream template internal validation, runtime subscriptions, skipped-branch scheduling, external AI/provider behavior and complete template parity. React and Svelte upstream examples remain evidence, not dependencies or runtime proofs. Unit 4 execution, Unit 6 capabilities, Unit 8 full-profile integration and collector-side OTLP tests remain separate acceptance boundaries.

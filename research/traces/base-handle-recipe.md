# Base Handle recipe trace

## Production paths

- **Vanilla:** The public package entry exports `createFlowBaseHandle` and its option type (`apps/vanilla/src/public.ts:74-76`). The helper builds a `FlowHandle` descriptor from the typed ID, kind, and side (`apps/vanilla/src/base-handle.ts:1-22`). The production canvas turns decoded node handles into native buttons, adds side/kind classes and handle data, and supplies an accessible label (`apps/vanilla/src/mount-flow.ts:1328-1340`). Focus and connection gestures stay in the canvas interaction path; the recipe adds no competing DOM event layer.
- **Vue:** The package entry exports `FlowBaseHandle` (`packages/vue/src/public.ts:47`). The component renders an original label and kind/side description from caller props (`packages/vue/src/base-handle.ts:12-49`). `FlowCanvas` creates the actual focusable button for each decoded `FlowNode.handles` entry and binds its keyboard connection handler (`packages/vue/src/flow-canvas.ts:4109-4120`). The component is presentation only; FlowCanvas owns connection acceptance and state.
- **Foldkit:** The package entry exports `createFoldkitBaseHandle` (`packages/foldkit/src/public.ts:94`). Its `HtmlBuilder` helper creates an original aria-hidden label and direction view with side/kind metadata (`packages/foldkit/src/base-handle.ts:4-31`). The production graph view creates each focusable handle button, accessible name, and keyboard activation message from the runtime node (`packages/foldkit/src/graph.ts:2875-2893`). The app renderer composes the package helper inside the runtime-owned node (`apps/foldkit/src/main.ts:156-192`).

## Conformity and deviations

- **Conforming within the bounded outcome:** Each host exposes an original handle presentation and preserves focusable canvas-owned connection controls. The mounted tests observe accepted and rejected connection outcomes through each host's production interaction path. Vanilla returns the canonical serializable handle descriptor; Vue provides a native component; Foldkit provides an `HtmlBuilder` view. This confirms local Flow behavior only.
- **Intentionally different:** The recipe does not own connection lifecycle, measurement, or graph state. The host canvas/runtime retains those responsibilities. The three exports therefore have host-native shapes and are not forced into a shared rendering abstraction.
- **Unverified:** No current-site or pinned xyflow UI comparison was run, so styling, option-level and accessibility parity are unverified. The tests cover the documented kinds/sides and selected acceptance/rejection cases, not every handle mode, duplicate ID behavior, screen-reader presentation, or package-archive consumption of this new recipe. The test boundary is the three local production routes listed above.

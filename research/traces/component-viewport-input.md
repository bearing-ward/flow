## Production viewport path

The React public `defaultViewport` enters ZoomPane and XYPanZoom (`packages/react/src/container/ZoomPane/index.tsx:77`, `packages/system/src/xypanzoom/XYPanZoom.ts:89`). XYPanZoom clamps zoom before constructing the initial transform. This is initialization behavior, separate from a later wheel operation. The viewport subscriber writes the rendered transform (`packages/react/src/container/Viewport/index.tsx:20`).

Flow's positive-zoom runtime schema remains strict (`packages/core/src/domain/flow-runtime.schema.ts:43`). The new initialization boundary decodes finite x/y/zoom and ordered positive limits, then clamps before producing runtime state (`packages/core/src/domain/flow-initial-viewport.ts:6`). Decode success and failure use structured logs and the existing host-mount span. No high-frequency input logging or exporter is added.

Vanilla's public `mountFlow` decodes its mount options, normalizes the initial viewport, and creates the host (`apps/vanilla/src/mount-flow.ts:13986`). The mount schema permits finite zoom before normalization (`apps/vanilla/src/mount-flow.ts:494`). Host constraints and DOM ownership remain in `apps/vanilla/src/mount-flow.ts:2242`. Vue decodes effective limits, including the public minZoom/maxZoom overrides, then normalizes the default viewport before its owned shallow ref is created (`packages/vue/src/flow-canvas.ts:1192`, `packages/vue/src/flow-canvas.ts:1270`). Controlled owner replacements retain their existing ownership boundary.

Foldkit's public `createProgram` constructs the initial graph before Runtime embeds it (`packages/foldkit/src/application.ts:3643`). Graph initialization normalizes the viewport before the serializable Model is validated (`packages/foldkit/src/graph.ts:8307`). The baseline negative zoom reached Model validation inside Runtime and produced Application Crash. The repaired model contains zoom 0.5 before Runtime starts. The viewport client also normalizes its cached initial value so disposal before a first response cannot return negative zoom (`packages/foldkit/src/application.ts:491`).

## Initial node extent conflict

React adopts the user node into its internal lookup, using available dimensions rather than inventing a default measured size (`packages/system/src/utils/store.ts:129`). clampPosition subtracts dimensions from each maximum (`packages/system/src/utils/general.ts:20`). Measurement can later recalculate absolute positions (`packages/system/src/utils/store.ts:401`). The upstream component case supplies no measured dimensions and asserts the initial transform at (50,50) (`examples/react/cypress/components/reactflow/view-props.cy.tsx:193`). This is distinct from the utility case that supplies dimensions and expects maximum minus size (`examples/react/cypress/components/utils/adopt-user-nodes.cy.ts:48`). For a measured 150x44 node in this 50x50 extent, the upstream formula computes (-100,6), whereas Flow centering computes (-50,6). These are source-derived calculations, not a live React capture at the component test's 500ms boundary.

Vanilla renders a measured 150x44 node at (-50,6). Its public nodeExtent reaches boundedNodePosition, which uses measured dimensions and constrainNodePosition; restoreAdoptedPosition holds a display override while the document remains authoritative (`apps/vanilla/src/mount-flow.ts:2776`, `apps/vanilla/src/mount-flow.ts:2950`, `apps/vanilla/src/mount-flow.ts:4211`). Core deliberately centers oversized nodes (`packages/core/src/domain/flow-node-extent.schema.ts:25`). This is already documented as an intentional difference in `research/traces/node-extents.md:31`. The existing core and mounted extent tests are therefore preserved.

Vue and Foldkit remain at (200,200). Their render graphs do not adopt nodeExtent during initialization (`packages/vue/src/flow-canvas.ts:1546`, `packages/foldkit/src/graph.ts:7324`). These are missing adoption behaviors, not intentional passes. The 150-pixel node exceeds the 50-pixel extent, so choosing an initial adoption repair would also choose between the documented Flow oversized policy and the upstream unmeasured-adoption policy. Under the task's conflict rule, record this conflict and defer that repair. Retain fail entries for these two hosts. Later assertions after the x failure remain unverified.

## Production native input path

React's node wrapper invokes onClick even if zero-threshold drag-start selection already ran (`packages/react/src/components/NodeWrapper/index.tsx:108`). XYDrag passes nodeClickDistance to d3's click admission (`packages/system/src/xydrag/XYDrag.ts:306`). Vanilla's real pointer release formerly suppressed every activated drag except when selectNodesOnDrag was false. A stationary zero-threshold drag is activated, so selection succeeded but the native click callback never ran. The release now admits a stationary click within nodeClickDistance regardless of selection ownership (`apps/vanilla/src/mount-flow.ts:9351`, `apps/vanilla/src/mount-flow.ts:9435`). Existing capture, drag completion, selection, and moved-click suppression remain exercised by node-input and node-threshold browser suites.

React installs its double-click callback on NodeWrapper (`packages/react/src/components/NodeWrapper/index.tsx:104`). Foldkit's baseline document observer installed contextmenu and mouse listeners but no dblclick listener. Window capture receipts prove that native contextmenu and dblclick reached Node 1. The new scoped document dblclick listener resolves the owning node and emits an observed mouse record (`packages/foldkit/src/mouse-observation.ts:196`, `packages/foldkit/src/mouse-observation.ts:317`). The record enters the pointer resource queue (`packages/foldkit/src/graph.ts:6776`), passes through application update, and becomes an interactionEvents publication (`packages/foldkit/src/application.ts:2685`). The event schema and optional callback owner now accept onNodeDoubleClick (`packages/foldkit/src/graph.ts:625`, `packages/foldkit/src/interaction-handlers.ts:10`). Listener disposal removes the dblclick listener with the other scoped listeners. This path does not repurpose viewport double-click zoom or log mouse moves.

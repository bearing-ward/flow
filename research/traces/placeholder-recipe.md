# Placeholder recipe

This trace follows the production /ui-recipes/placeholder/ routes. Each host starts with an empty accepted document. The app owns the action callback and node data; the reusable UI export only presents the native empty-state button. The action is disabled or removed after activation so one empty-state action cannot submit duplicate nodes while an edit is pending.

## Vanilla production path

apps/vanilla/ui-recipes/placeholder/index.html loads apps/vanilla/src/ui/placeholder-test.ts. The route mounts an empty uncontrolled graph and creates the public createFlowPlaceholder button (apps/vanilla/src/ui/placeholder-test.ts:21-32, :36-57; apps/vanilla/src/ui/placeholder.ts:7-18). Its callback calls controller.addNodes with app-owned id, label, and graph position, then displays the accepted document node count (apps/vanilla/src/ui/placeholder-test.ts:36-53). controller.addNodes converts the request to an add-nodes transaction and applies it through the host (apps/vanilla/src/mount-flow.ts:9177-9185).

The host creates an article node with the accepted label, applies the accepted graph position, and installs keyboard interaction state (apps/vanilla/src/mount-flow.ts:4833-4859, :1284-1305). The DOM position is derived from the graph position by applyNodePosition (apps/vanilla/src/mount-flow.ts:1251-1256). The browser test checks the rendered accessible node, keyboard selection, a single accepted node, and pointer activation after reload (apps/vanilla/e2e/placeholder-recipe.e2e.ts:3-26). The route registers `controller.destroy` on pagehide (apps/vanilla/src/ui/placeholder-test.ts:71-73).

## Vue production path

apps/vue/ui-recipes/placeholder/index.html loads apps/vue/src/placeholder-test.ts, which decodes an empty document and renders FlowCanvas with the public FlowPlaceholder component in its canvas slot (apps/vue/src/placeholder-test.ts:8-12, :48-57). FlowPlaceholder renders a native labeled button and emits the caller-owned activation event (packages/vue/src/ui/placeholder.ts:4-24). The route calls useFlow().addNodes, reports accepted node count, retries the visible empty-state action after an edit rejection, and subscribes to accepted public state so keyboard selection is observable; the subscription is stopped on component unmount (apps/vue/src/placeholder-test.ts:12-35, :48-59). addNodes constructs an add-nodes edit against the editor (packages/vue/src/use-flow.ts:470-478).

FlowCanvas renders visible graph nodes from graph.value.orderedNodes; each wrapper takes its graph-derived position and remains focusable unless the node contract disables focus. Enter or Space on the wrapper publishes a public selection change (packages/vue/src/flow-canvas.ts:4093-4112, :4288-4309, :4318-4344, :5280-5290). The browser test checks accepted rendered content, keyboard focus and selection, exactly one node, then reloads and checks the empty route is mounted again (apps/vue/e2e/placeholder-recipe.e2e.ts:3-20). The route unmounts the Vue app on pagehide and the component disposes its public state subscription on unmount (`subscribeState` at apps/vue/src/placeholder-test.ts:16-20; `onBeforeUnmount(stopState)` at :22; app creation/mount and pagehide unmount at :59-67). Listener and subscription leak testing is not claimed. The rejected-edit retry branch is present in source but has no dedicated failure-path assertion.

## Foldkit production path

apps/foldkit/ui-recipes/placeholder/index.html loads the app route. The route embeds a Runtime with an empty decoded document and presents the public createFoldkitPlaceholder button above the canvas viewport. Its activation registers a unique request ID, sends the add-nodes transaction through the public Runtime edit port, and waits for the result before removing the action and showing the accepted node count; failed sends or edit responses restore the action and report rejection (apps/foldkit/ui-recipes/placeholder/main.ts:97-146; package button export: packages/foldkit/src/ui/placeholder.ts:7-19). The application forwards the public edit request to the graph update loop, then publishes the accepted edit result (packages/foldkit/src/application.ts:1851-1858, :852-864). The snapshot control sends a public node snapshot request and reports the accepted selected state (apps/foldkit/ui-recipes/placeholder/main.ts:148-166). Runtime disposal is wired to pagehide (apps/foldkit/ui-recipes/placeholder/main.ts:168-170).

The graph view derives each rendered node's absolute position and measured size, applies those values to DOM styles, and outputs a focusable node plus its selection control (packages/foldkit/src/graph.ts:2844-2876, :2876-2889, :2986-3012). The recipe's local layout places the empty-state action above the viewport stacking layer so canvas pointer handling cannot cover it (apps/foldkit/ui-recipes/placeholder/placeholder.css:8-25). The browser test covers keyboard activation, one accepted rendered node, a pointer activation after reload, keyboard selection confirmed from an accepted snapshot, and an empty route after another reload (apps/foldkit/e2e/placeholder-recipe.e2e.ts:3-32). The original E2E confirms route remount; Plan 076 adds the explicit pending-request shutdown test below. Listener leak counts remain unverified. The rejected-send/edit recovery branches are present in source but have no dedicated failure-path assertion.

## Conformity and deviations

- **Conforming:** All three production routes begin with an empty accepted graph, expose a keyboard-operable native action, submit one caller-owned node through the host's public edit API, and verify accepted rendered output. Foldkit also verifies pointer activation after the route remount.
- **Intentionally different:** The reusable action is a DOM factory in Vanilla and Foldkit and a native Vue component. Each route delegates graph edits to its owning host API. Foldkit places its empty-state overlay above the runtime viewport because the viewport otherwise intercepts pointer events.
- **Unverified:** The dated UI catalog page and pinned source do not establish the complete Placeholder behavior or a runnable equivalent. No upstream option-by-option or runtime comparison is claimed. Package archive consumption, assistive-technology behavior, and full lifecycle leak coverage remain unverified.

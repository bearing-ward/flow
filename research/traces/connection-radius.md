# Connection radius targeting

Status: traced against pinned xyflow commit `0a1f9575b25679f2880175de8d3eae21aedde921`. Reference paths below are relative to `research/artifacts/xyflow/0a1f9575b25679f2880175de8d3eae21aedde921/`.

## Reference production path

React exposes `connectionRadius?: number` as the radius around a handle for dropping a connection and initializes it to 20 (`packages/react/src/types/component-props.ts:650`, `packages/react/src/store/initialState.ts:146`). `ReactFlow` passes the prop into its renderer and `StoreUpdater` tracks changes (`packages/react/src/container/ReactFlow/index.tsx:137`, `packages/react/src/container/ReactFlow/index.tsx:244`, `packages/react/src/components/StoreUpdater/index.tsx:64`). On a source-handle pointer press, React's `Handle` reads the current store value and calls the shared `XYHandle.onPointerDown` (`packages/react/src/components/Handle/index.tsx:139`, `packages/react/src/components/Handle/index.tsx:152`). Svelte exposes the same option, derives a 20 default in its store, and passes that value from its handle pointer handler to the same shared function (`packages/svelte/src/lib/container/SvelteFlow/types.ts:201`, `packages/svelte/src/lib/store/initial-store.svelte.ts:378`, `packages/svelte/src/lib/components/Handle/Handle.svelte:113`, `packages/svelte/src/lib/components/Handle/Handle.svelte:121`). React edge reconnection also passes the radius to this function (`packages/react/src/components/EdgeWrapper/EdgeUpdateAnchors.tsx:53`, `packages/react/src/components/EdgeWrapper/EdgeUpdateAnchors.tsx:80`).

After the connection drag crosses its separate threshold, each pointer move converts the pointer from pane coordinates into renderer coordinates and asks `getClosestHandle` for a candidate (`packages/system/src/xyhandle/XYHandle.ts:128`, `packages/system/src/xyhandle/XYHandle.ts:147`, `packages/system/src/utils/general.ts:168`). The search first limits nodes using a rectangular overlap around the pointer with `connectionRadius + 250`; this is a candidate filter, not the final acceptance radius (`packages/system/src/xyhandle/utils.ts:4`, `packages/system/src/xyhandle/utils.ts:26`, `packages/system/src/xyhandle/utils.ts:37`). It checks both source and target handle bounds, excludes the exact starting handle, measures Euclidean distance to each handle's center in renderer coordinates, and retains candidates at **distance less than or equal to** the radius (`packages/system/src/xyhandle/utils.ts:40`, `packages/system/src/xyhandle/utils.ts:43`, `packages/system/src/xyhandle/utils.ts:48`, `packages/system/src/xyhandle/utils.ts:51`, `packages/system/src/utils/edges/positions.ts:99`). The nearest center wins; on a distance tie, the opposite handle type wins if present (`packages/system/src/xyhandle/utils.ts:56`, `packages/system/src/xyhandle/utils.ts:69`). Since the conversion divides by viewport zoom, the configured radius is measured in renderer or flow units, not a fixed number of screen pixels (`packages/system/src/utils/general.ts:168`).

The candidate is then passed to `isValidHandle`. That function uses `elementFromPoint` and prefers a handle **directly under the pointer** over the nearest-center candidate. It checks DOM `connectable` and `connectableend` classes, strict or loose connection mode, and the caller's validator (`packages/system/src/xyhandle/XYHandle.ts:161`, `packages/system/src/xyhandle/XYHandle.ts:267`, `packages/system/src/xyhandle/XYHandle.ts:272`, `packages/system/src/xyhandle/XYHandle.ts:275`, `packages/system/src/xyhandle/XYHandle.ts:307`). Thus a visible large handle can still be selected when its center lies outside the radius. `isConnectionValid` reports a valid handle as valid even without a nearest-center candidate; with a nearby but invalid handle it reports false rather than null (`packages/system/src/xyhandle/utils.ts:117`). The pointer connection state receives the resolved handle and validity. For a valid handle, its endpoint snaps to that handle's center; otherwise it stays at the pointer (`packages/system/src/xyhandle/XYHandle.ts:176`, `packages/system/src/xyhandle/XYHandle.ts:183`). React and Svelte connection-line components render that state and its validity styling (`packages/react/src/components/ConnectionLine/index.tsx:38`, `packages/react/src/components/ConnectionLine/index.tsx:52`, `packages/react/src/components/ConnectionLine/index.tsx:72`, `packages/svelte/src/lib/components/ConnectionLine/ConnectionLine.svelte:63`). On pointer release, the shared handler calls `onConnect` only if a candidate or DOM handle exists and the connection is valid (`packages/system/src/xyhandle/XYHandle.ts:201`, `packages/system/src/xyhandle/XYHandle.ts:207`).

The separate click-to-connect path calls `XYHandle.isValid` for a clicked DOM handle without invoking `getClosestHandle`; connection radius does not govern that path (`packages/react/src/components/Handle/index.tsx:210`, `packages/system/src/xyhandle/XYHandle.ts:323`).

## Flow production path

The Vanilla public mount option is optional in `FlowMountOptionsSchema`, then validated with the other mount inputs before it reaches `mountFlow` (`apps/vanilla/src/mount-flow.ts:280`, `apps/vanilla/src/mount-flow.ts:311`, `apps/vanilla/src/mount-flow.ts:8969`, `apps/vanilla/src/mount-flow.ts:9637`). Its core schema accepts a finite nonnegative radius, and `nearestConnectionTarget` chooses the closest **target** handle center at distance less than or equal to that radius. It excludes the starting handle and resolves equal distances deterministically by node ID, then handle ID (`packages/core/src/domain/flow-connection-radius.schema.ts:16`, `packages/core/src/domain/flow-connection-radius.schema.ts:29`, `packages/core/src/domain/flow-connection-radius.schema.ts:43`, `packages/core/src/domain/flow-connection-radius.schema.ts:52`, `packages/core/src/domain/flow-connection-radius.schema.ts:56`).

The Vanilla browser host's `connectionTargetAt` collects rendered handle centers and the pointer in client coordinates, then calls the core nearest-target resolver with the configured radius unchanged (`apps/vanilla/src/mount-flow.ts:2515`, `apps/vanilla/src/mount-flow.ts:2522`). Therefore this host interprets the public radius in screen-space CSS pixels; zoom does not change its effective screen radius. Pointer movement and release share this resolver, and click-to-connect resolves the clicked handle without consulting the radius (`apps/vanilla/src/mount-flow.ts:611`, `apps/vanilla/src/mount-flow.ts:623`, `apps/vanilla/src/mount-flow.ts:2550`, `apps/vanilla/src/mount-flow.ts:2565`, `apps/vanilla/src/mount-flow.ts:2769`, `apps/vanilla/src/mount-flow.ts:2811`).

The Vue adapter validates its prop through `ConnectionRadiusSchema`, converts pointer and measured-handle coordinates into graph coordinates, then passes `connectionRadius / viewport.zoom` to the shared core resolver (`packages/vue/src/flow-canvas.ts:515`, `packages/vue/src/flow-canvas.ts:1048`, `packages/vue/src/flow-canvas.ts:3074`). This preserves a screen-space CSS-pixel radius at any zoom. Its production E2E test verifies a nearby release and an outside-radius release at 2x, plus direct-hit acceptance with radius zero (`apps/vue/e2e/interaction-lifecycle.e2e.ts:1030`, `apps/vue/e2e/interaction-lifecycle.e2e.ts:1082`, `apps/vue/e2e/interaction-lifecycle.e2e.ts:1117`).

Foldkit accepts the radius through `GraphInteractionOptions`; `Application.createProgram` forwards those options to `Graph.initialModel`, which merges the supplied value over the 20-unit default (`packages/foldkit/src/application.ts:2566`, `packages/foldkit/src/application.ts:2579`, `packages/foldkit/src/graph.ts:424`, `packages/foldkit/src/graph.ts:440`, `packages/foldkit/src/graph.ts:4020`, `packages/foldkit/src/graph.ts:4029`). Handle centers and pointer coordinates are in graph units. Preview targeting, reconnection candidate selection, and pointer-release resolution divide the configured CSS-pixel radius by viewport zoom before comparing those graph-space values (`packages/foldkit/src/graph.ts:2452`, `packages/foldkit/src/graph.ts:2510`, `packages/foldkit/src/graph.ts:3554`). A production E2E case checks preview candidate and release behavior on both sides of the zoom conversion: at 2x, 30 screen pixels is rejected; at 0.5x, 15 screen pixels is accepted (`apps/foldkit/e2e/interaction-lifecycle.e2e.ts:1302`).

## Flow test path

The Vanilla host has a zoom-1 near-miss/release test and zoom-0.5/2 preview and validation cases (`apps/vanilla/e2e/advanced-gestures.e2e.ts:2178`, `apps/vanilla/e2e/flow-followups.e2e.ts:293`, `apps/vanilla/e2e/flow-followups.e2e.ts:299`). These Flow tests exercise browser hosts; the pinned React/Svelte tests do not cover zoom scaling or radius near misses.

## Conformity and deviations

- **Conforming:** Vanilla, Vue, and Foldkit accept the public radius and keep it fixed in screen-space CSS pixels under zoom; Vue and Foldkit convert the value to graph units by dividing by zoom, while Vanilla compares screen coordinates directly. Core tests cover the exact geometric boundary, and host tests cover near/far releases at multiple zooms. Vanilla and Vue also prefer the handle under the pointer before falling back to radius-based nearest-target search.
- **Intentionally different:** Flow's configured CSS-pixel radius stays fixed on screen under zoom, while the pinned xyflow radius is measured in renderer/flow units and scales on screen with zoom. Flow searches target-kind handles only and resolves ties by IDs; the reference searches both handle types and prefers the opposite type on a distance tie. Flow's hover feedback is an outline on the candidate handle (`apps/vanilla/src/style.css:175`, `apps/vanilla/src/style.css:180`), while the reference passes validity into its connection-line renderers (`packages/react/src/components/ConnectionLine/index.tsx:38`, `packages/svelte/src/lib/components/ConnectionLine/ConnectionLine.svelte:63`).
- **Unverified:** Foldkit release targeting resolves nearest handle centers and has no explicit DOM direct-hit override, so a hit on an unusually large handle whose center is beyond the radius is not established as equivalent to Vanilla, Vue, or xyflow. No Flow browser test asserts the exact geometric radius boundary; the core unit test does. The pinned suite does not assert zoom scaling, a radius near miss, or a boundary. No source or test here claims broader parity.

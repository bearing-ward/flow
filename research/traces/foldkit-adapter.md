# Foldkit adapter lifecycle and shared contract

## Production path

The browser entry is `apps/foldkit/index.html`, which loads `src/main.ts`. The entry decodes the initial two-node document through the core document decoder and starts the Foldkit element runtime with the selected container and viewport (`apps/foldkit/src/main.ts:1-17`). The root `makeElement` receives the container, ports, init, update, view, and subscriptions; its model embeds the typed graph child (`packages/foldkit/src/application.ts:94-118`). The root model and host action / outgoing-change messages derive from Effect Schemas (`packages/foldkit/src/application.ts:14-37`).

The graph child model contains the core `FlowDocument` and `Viewport`, separate controlled/uncontrolled modes, allowed connection targets, and a transient pointer session (`packages/foldkit/src/graph.ts:19-35`). Its `Message` union is schema-derived, and `OutMessage` carries the shared `FlowChangeSchema` (`packages/foldkit/src/graph.ts:37-64`). The graph view computes visible nodes from document positions and viewport values, renders nodes and edges keyed by schema IDs, and converts DOM pointer input to typed child messages (`packages/foldkit/src/graph.ts:151-196`). The root uses Foldkit's typed submodel mapping to route child messages and `Update.foldChild` to translate semantic child output into a root output command (`packages/foldkit/src/application.ts:40-92`).

On pointer down, the child stores a transient session. While that session is active, its model-scoped subscription listens for document-level pointerup and pointercancel; the root lifts that subscription through the graph child boundary (`packages/foldkit/src/graph.ts:198-213`, `packages/foldkit/src/application.ts:108-117`). Node movement calculates deltas in flow units from the viewport zoom and delegates document changes to the core `applyNodePositionChange` function (`packages/foldkit/src/graph.ts:72-86`, `packages/foldkit/src/graph.ts:122-134`). Connection completion checks declared source and target handles, target allow-list membership, and core `validateFlowConnection`; successful connections use `nextConnectionEdge` to create the shared `edge-add` change (`packages/foldkit/src/graph.ts:100-120`). Controlled mode emits either candidate without changing the authoritative document; uncontrolled mode applies the candidate before publishing it. The root's output command emits the change through the `changes` port (`packages/foldkit/src/application.ts:40-57`).

## Test path

The adapter has an isolated Playwright config and Vite server on port 4175 (`apps/foldkit/playwright.config.ts:1-14`). Its browser driver mounts the same fixture definitions imported by the vanilla adapter and drives host-specific pointer events/selectors (`apps/foldkit/e2e/conformance.ts:1-53`). The shared suite compares the same expected snapshots and semantic output for all shared fixtures; separate cases verify keyed identity, emitted movement, disposal, and controlled edge acknowledgement (`apps/foldkit/e2e/shared-conformance.e2e.ts:5-69`). The harness runs the actual Foldkit runtime through `Runtime.embed`, subscribes to its output port, and disposes the runtime before measuring post-disposal output and remaining DOM (`apps/foldkit/e2e/test-harness.ts:20-71`).

## Conformity and deviations

- **Conforms:** Foldkit uses schema-derived Flow documents, viewports, commands, and semantic changes; keyed nodes retain identity during keyed updates. The six shared fixture definitions use the same expected outputs as vanilla. Test boundary: `bun run test:conformance:foldkit` and the dedicated smoke/controlled-connection browser cases.
- **Intentionally different:** this adapter is a small DOM canvas with basic node movement and handle connections. It omits the vanilla adapter's renderer registry, measured geometry, SVG paths, and broader gesture surface. This keeps framework lifecycle code in the app and graph meaning in core. Test boundary: only the listed shared fixtures and the adapter smoke cases are asserted; no full feature or pixel parity is claimed.
- **Unverified:** visual parity and Foldkit Model state preservation across Vite hot reload. The tests mount, update, and dispose the runtime but do not assert those behaviors.

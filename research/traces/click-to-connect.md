# Click-to-connect

Status: traced against pinned xyflow commit `0a1f9575b25679f2880175de8d3eae21aedde921`. Reference paths below are relative to `research/artifacts/xyflow/0a1f9575b25679f2880175de8d3eae21aedde921/`.

## React production path

The public `connectOnClick` prop allows a source-handle click or tap followed by a target-handle click and defaults to `true` (`packages/react/src/types/component-props.ts:588`). `ReactFlow` passes the prop through to its renderer (`packages/react/src/container/ReactFlow/index.tsx:126`, `packages/react/src/container/ReactFlow/index.tsx:221`). The store starts with `connectionClickStartHandle: null` and `connectOnClick: true` (`packages/react/src/store/initialState.ts:136`). `Handle` receives that configuration through context and attaches its click handler only when enabled (`packages/react/src/contexts/HandleConfigContext.tsx:13`, `packages/react/src/components/Handle/index.tsx:273`).

On the first click, the handler requires a node and a start-connectable handle, calls `onClickConnectStart`, and stores the handle's node ID, type, and handle ID (`packages/react/src/components/Handle/index.tsx:185`, `packages/react/src/components/Handle/index.tsx:198`). The handle selector reads this start handle and marks it `clickconnecting`; while a click connection is pending, the DOM class `connectionindicator` marks end-connectable handles (`packages/react/src/components/Handle/index.tsx:63`, `packages/react/src/components/Handle/index.tsx:77`, `packages/react/src/components/Handle/index.tsx:255`). This is the visible pending state. The click path itself does not update the pointer-drag connection state or draw a connection line (`packages/react/src/components/Handle/index.tsx:202`, `packages/react/src/components/Handle/index.tsx:210`).

On the next handle click, `Handle` calls `XYHandle.isValid` with the saved start handle, clicked handle, connection mode, node lookup, and handle or store validator (`packages/react/src/components/Handle/index.tsx:208`). The shared validator resolves the clicked handle from the DOM, constructs source and target endpoints, requires `connectable` and `connectableend`, enforces strict opposite-handle types or loose different-handle semantics, and runs the caller validator (`packages/system/src/xyhandle/XYHandle.ts:267`, `packages/system/src/xyhandle/XYHandle.ts:287`, `packages/system/src/xyhandle/XYHandle.ts:298`, `packages/system/src/xyhandle/XYHandle.ts:307`). A valid result reaches `onConnectExtended`, which updates default-owned edges and calls the flow-level and handle-level callbacks (`packages/react/src/components/Handle/index.tsx:124`, `packages/react/src/components/Handle/index.tsx:227`). The handler calls `onClickConnectEnd` and clears the saved start handle after this second click, including an invalid second click (`packages/react/src/components/Handle/index.tsx:231`).

React's `cancelConnection` resets the pointer-drag connection state, while store `reset` reinstates the initial state, including the null click start (`packages/react/src/store/index.ts:442`, `packages/react/src/store/index.ts:451`, `packages/react/src/store/initialState.ts:136`). The traced click handler has no separate pane-click or Escape cancellation branch; a second handle click clears it (`packages/react/src/components/Handle/index.tsx:185`, `packages/react/src/components/Handle/index.tsx:236`).

## Svelte production path

The public `clickConnect` prop toggles handle-click connections (`packages/svelte/src/lib/container/SvelteFlow/types.ts:428`). The Svelte store derives it from props with a `true` default and keeps `clickConnectStartHandle` separately from the pointer-drag connection (`packages/svelte/src/lib/store/initial-store.svelte.ts:412`). `Handle` attaches `onclick` only when enabled (`packages/svelte/src/lib/components/Handle/Handle.svelte:225`).

The first click requires a start-connectable handle, calls `onclickconnectstart`, and saves node ID, type, and handle ID (`packages/svelte/src/lib/components/Handle/Handle.svelte:145`). Its `connectionindicator` class marks end-connectable handles while a click connection is pending (`packages/svelte/src/lib/components/Handle/Handle.svelte:220`). The second click calls the same shared `XYHandle.isValid` with the saved handle and Svelte node lookup (`packages/svelte/src/lib/components/Handle/Handle.svelte:156`). On success, `onConnectExtended` runs `onbeforeconnect`, adds the edge to the store, and calls `onconnect` (`packages/svelte/src/lib/components/Handle/Handle.svelte:102`, `packages/svelte/src/lib/components/Handle/Handle.svelte:177`). The handler calls `onclickconnectend` and clears the start handle whether validation succeeded or failed (`packages/svelte/src/lib/components/Handle/Handle.svelte:181`). Store reset also clears it (`packages/svelte/src/lib/store/initial-store.svelte.ts:476`).

## Flow production path

The vanilla host exposes an optional `connectOnClick` mount setting, while its Schema-derived pending click state holds the source node and handle IDs (`apps/vanilla/src/mount-flow.ts:78`, `packages/core/src/domain/flow-connection.schema.ts:15`, `apps/vanilla/src/mount-flow.ts:292`). A source-handle pointer press still starts the drag path. When release stays within three screen pixels of that same handle, the host changes to click mode and suppresses the following synthetic canvas click (`apps/vanilla/src/mount-flow.ts:2229`, `apps/vanilla/src/mount-flow.ts:2241`). `beginClickConnection` marks the source handle `connecting`, focuses the canvas, draws a preview anchored at the source, and records the semantic start boundary (`apps/vanilla/src/mount-flow.ts:2190`).

The canvas click handler resolves clicked handles from the current document (`apps/vanilla/src/mount-flow.ts:2354`). A second click on the same source cancels; another source replaces the pending start; a target clears pending state and calls the shared commit path (`apps/vanilla/src/mount-flow.ts:2380`). That path runs the core's source-to-target and duplicate validation, then publishes an `edge-add` change and records completion (`apps/vanilla/src/mount-flow.ts:2147`, `packages/core/src/domain/flow-connection.schema.ts:54`, `apps/vanilla/src/mount-flow.ts:2168`). `clearClickConnection` removes both preview and `connecting` class (`apps/vanilla/src/mount-flow.ts:476`). Clicking outside a handle, pressing Escape, removing or hiding the source in a document update, and destroying the host cancel a pending click connection (`apps/vanilla/src/mount-flow.ts:2419`, `apps/vanilla/src/mount-flow.ts:2522`, `apps/vanilla/src/mount-flow.ts:931`, `apps/vanilla/src/mount-flow.ts:2795`).

## Flow test path

The browser test mounts an uncontrolled graph with `connectOnClick: true` (`apps/vanilla/e2e/gesture-options.e2e.ts:56`). It clicks a source and checks the `connecting` class and preview, presses Escape and checks cleanup with no published change, clicks the same source twice to cancel, then clicks source and target across a viewport update and checks a rendered edge plus `edge-add` (`apps/vanilla/e2e/gesture-options.e2e.ts:276`). The separate drag helper uses mouse down, move, and up (`apps/vanilla/e2e/canvas.e2e.ts:95`). These Flow tests do not run the pinned xyflow adapters. An invalid second-handle click and touch-generated click remain outside this browser test's assertions.

## Conformity and deviations

- **Conforming:** Flow and both reference adapters retain the first clicked handle and validate a proposed second endpoint before creating an edge. Flow's browser test covers a successful two-click connection and Escape and same-source cancellation. The pinned reference tests cover drag connections only.
- **Intentionally different:** Flow uses strict source-to-target endpoints and a semantic `edge-add` change. The reference supports loose mode and adapter-specific edge ownership. Flow also draws a stationary pending preview and explicitly cancels on pane click and Escape; the traced reference click handlers indicate pending handles without a line and clear on a second handle click or store reset.
- **Unverified:** The Flow browser test does not assert invalid target clicks or touch-generated clicks. The pinned tests do not establish click behavior, so these production-source similarities do not prove adapter parity.

## Workspace package outputs

`@flow/core` ships its public JavaScript and declarations from `dist/` and declares the exact `effect` release `4.0.0`. `@flow/vanilla` ships its public JavaScript, declarations, and stylesheet and depends on that Effect release and `@flow/core`. `@flow/vue` ships its public entry point and stylesheet, depends on `@flow/core` and Effect, and declares Vue `^3.5.43` as a peer. `@flow/foldkit` ships its public entry point and stylesheet, depends on `@flow/core` and Effect, and declares Foldkit `0.169.0` and `@effect/platform-browser` `4.0.0` as peers. The private Vue and Foldkit demos consume their adapters through package exports; the Foldkit demo declares its runtime peers directly. `bun run test:consumer` packs all four packages, installs them into three separate clean consumers without workspace aliases or source access, checks peer resolution, typechecks public imports, and exercises host behavior, styles, and teardown in Chromium. Core is also imported by Bun with DOM globals absent. These checks cover the named fixtures; they do not establish complete feature parity or prove server-side rendering for browser adapters. The workspace root pins `@effect/platform-bun`, `@effect/platform-browser`, `@effect/platform-node-shared`, and `effect` to `4.0.0`, matching Foldkit's exact peers and preventing a mixed Effect release in the lockfile. Vite, TypeScript, Bun, and Playwright remain workspace build or verification tools rather than runtime dependencies of the core package.

## Plan 147 toolchain compatibility

The workspace pins TypeScript 7.0.2 and Ultracite 8.0.2. Oxlint 1.89.0, `@oxlint/plugins` 1.89.0, and Oxfmt 0.74.0 already satisfy Ultracite 8's peer ranges, `^1.86.0` and `>=0.71.0 <1`, and remain pinned. The registry's stable versions were checked on 2026-10-25. Effect and its platform modules stay at 4.0.0 because Foldkit 0.169.0 and its Vite plugin require that release exactly.

### Release and migration evidence

Microsoft's [TypeScript 7 release announcement](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/#running-side-by-side-with-typescript-60) explains the native compiler and the missing compatible compiler API. The installed 7.0.2 package exposes version metadata at its root, plus unstable API entry points. It does not expose `createSourceFile`, `ScriptTarget`, or the legacy language service there. A runtime import confirmed that the native root has no `createSourceFile`, while `typescript-api` reports 5.9.3 and `ScriptTarget.Latest === 99`. This explicit alias follows the side-by-side approach while retaining the 5.x version required by this plan.

The [Ultracite 8.0.0 release notes](https://www.ultracite.ai/changelog/ultracite-8-0-0), [8.0.2 release notes](https://www.ultracite.ai/changelog/ultracite-8-0-2), and [upgrade guide](https://www.ultracite.ai/docs/upgrade) describe the supported Oxc ranges and configuration changes. The installed `references/upgrades/v8.md` was also reviewed. Flow uses the Oxlint core and Vitest presets with Oxfmt. It has no ESLint, Stylelint, Zed ESLint formatter, `init --quiet` integration, or `oxlint-tsgolint` installation requiring the v8 configuration migrations. No new rule overrides are needed. New test naming and promise return findings are fixed in source. The native compiler's side-effect import checking uses Vite's existing `vite/client` asset declarations for the browser hosts' CSS imports.

### Consumer findings

| --- | --- |

| Vue and Volar | No workspace or packed fixture installs `vue-tsc`, Volar, or `@vitejs/plugin-vue`, and there are no `.vue` source files. The adapter uses typed render functions and native `tsc`; the demo uses Vite directly. Microsoft documents that Volar's embedded compiler needs the legacy API. SFC tooling is outside the current verification boundary; no unused compatibility dependency is installed for it. |
| Vite 8.3.5 and plugins | [Vite's TypeScript documentation](https://vite.dev/guide/features.html#typescript) separates Oxc transpilation from compiler typechecking. The three app configs use the repository's `upstreamFixtureRoute`; the Foldkit app additionally uses `@foldkit/vite-plugin`. The plugin distribution has no runtime TypeScript import and its manifest lists TypeScript `^7.0.2` as a development dependency. App builds and browser suites exercise these transforms. |
| Foldkit plugin 0.28.0 | Retains Vite `^8.0.0` and Effect 4.0.0 peers. Its runtime transforms do not embed the TypeScript compiler API. The dedicated `test:foldkit:hmr` check covers model preservation and view identity in development; production builds alone do not establish HMR compatibility. |
| AST analysis | `scripts/architecture-rules.ts`, `scripts/check-docs.ts`, `scripts/check-api-member-contracts.ts`, `scripts/inventory-xyflow.ts`, `scripts/upstream-test-cases.ts`, and `apps/react-reference/fixture-source.ts` explicitly import `typescript-api`. ### Conformity and deviations

The toolchain follows the requested native TypeScript and Ultracite major versions. The pinned 5.9.3 API alias is an intentional exception for the named analysis consumers and frozen capture. Effect 4.0.0 is intentionally retained to satisfy Foldkit's exact peers. Vue SFC tooling and Effect editor diagnostics remain unverified because Flow does not run those paths. Full local verification covers the configured build, analysis, unit, packed-consumer, and browser paths; it does not establish editor compatibility or new upstream behavior parity.

## Pinned React reference host

`apps/react-reference` owns `@xyflow/react` 12.12.0 and `@xyflow/system` 0.0.83, matching the package versions in the immutable upstream revision. Published packages avoid rebuilding the upstream monorepo. Remove them with the reference host. They are private app dependencies and never enter Flow's published packages.

The host uses `react` and `react-dom` 18.2.0 to match the upstream Cypress `react18` mounts. `@types/react` 18.2.79 and `@types/react-dom` 18.2.25 typecheck the host. Other React major versions would change the lifecycle being measured. Remove these dependencies with the host.

`chai` 6.2.2 executes the 31 pinned utility test bodies in Chromium without translating their assertions. Reusing Vitest's Node runner would not provide the real DOM geometry required by `update-node-internals.cy.ts`. Remove Chai with that reference runner.

## Plan 162 optional obstacle router

`packages/routing-libavoid` owns the separately packed `@flow/routing-libavoid` integration and pins `libavoid-js@0.5.0-beta.5`. The private shared recipe composition opts in. The workspace's exact development dependency supports the raw pre-flight. Core, Vanilla, Vue and Foldkit package manifests and source imports reject engine dependencies through the architecture gate. Their bundles consume only engine-neutral core contracts.

The pinned beta was published on 2026-02-23. Registry size is 813,186 unpacked bytes, including a 492,029-byte WASM file. The missing exported declaration path and stale declaration constants require a boundary decoder for the actual Embind API. The library is unmodified. Its JavaScript and WASM load lazily and asynchronously. Three Chromium/Vite pre-flight projects pass. Packaging retains external peer/core/engine imports, includes the upstream licence, and exports the original WASM with a caller-owned URL.

LGPL-2.1-or-later requires distributors to retain notices and licence text, supply corresponding library source and build scripts as required, and preserve replacement or relinking rights. Application terms must allow personal modification and reverse engineering to debug it. Library modifications retain LGPL obligations. Separate packaging does not waive application bundling obligations. Replaceable modules/assets or suitable relinking materials are necessary. See the [upstream licence](https://github.com/Aksem/libavoid-js/blob/5062a42fbd82fff562afeebcbb7b1ed45eed8e75/LICENSE) and [adapter README](../packages/routing-libavoid/README.md). This is not legal advice.

Alternatives considered are existing ELK routing, under EPL-2.0, and a new Flow router. ELK does not establish incremental routing equivalence; a new router adds algorithm maintenance. Remove this integration when another implementation passes the router contract suite. Native WASM transaction execution is synchronous and cannot be interrupted mid-call; Effect cancellation and revision checks prevent late publication.

## Plan 165 optional image service

`packages/image-service` owns `@flow/image-service` and its exact runtime dependency `playwright@1.64.1`, Apache-2.0. The workspace already has `@playwright/test@1.64.1` as a development tool. That does not satisfy a production backend's browser-control dependency, so the optional service declares `playwright` directly. No Playwright import or dependency enters core or the host adapters. The architecture gate rejects both package imports and manifest dependencies there. The service build externalizes Playwright, Effect and core; the Docker runtime installs those production dependencies and serves prebuilt host assets.

The renderer decision is maintainer D13 in [unit 13](../plans/149-pro-delivery.md#13-server-side-image-service). Puppeteer was considered but would add a second browser automation library. A pure SVG/resvg implementation would require another restricted renderer and could not reuse the existing custom HTML renderers. Remove Playwright with this optional service, or replace it when another backend passes the same host-renderer, cancellation, readiness and resource-release acceptance tests. The host snapshot APIs and DOM-independent core export contract remain usable with another backend.

The matching `mcr.microsoft.com/playwright:v1.64.1-noble` container supplies Chromium and browser system dependencies. The [official Docker guide](https://playwright.dev/docs/docker) states that the browser image excludes the Playwright package; the runtime installs the pinned library separately. Bun 1.4.3 supplies the service runtime. The [browser lifecycle API](https://playwright.dev/docs/api/class-browser) and [screenshot API](https://playwright.dev/docs/screenshots) define the resources and PNG output used here. No other browser automation runtime is introduced.

The service composition bundles the unmodified [IBM Plex Sans variable font](https://github.com/google/fonts/tree/main/ofl/ibmplexsans), under SIL Open Font License 1.1, and preserves `OFL.txt` beside it. Its owner is `apps/shared/image-service/assets`; the host builds copy that shared font and the local SVG Flow mark. System fonts were considered but cannot provide the same glyph metrics across macOS and Linux. Remove the font with the capture recipe or replace it only alongside updated rendering proof. Approved scope is documented in [server image creation](server-image-service.md#supported-renderers-and-assets).

## Plan 164 optional collaborative rooms

`packages/collaboration-yjs` owns `@flow/collaboration-yjs`. Application composition in `@flow/recipe-shared` opts in. Its runtime dependencies are MIT `yjs` 13.6.33 for field registers, transaction origins, duplicate-update handling and selective local undo, and MIT `y-websocket` 3.1.0 for room transport and awareness. Flow core and Effect 4.0.0 are external peers. The architecture gate rejects Yjs, y-websocket, y-protocols, the server and this optional package in core and all reusable host adapter sources/manifests. No dependency enters the core or host bundles.

The MIT `@y/websocket-server` 0.1.1 development dependency owns the anonymous localhost acceptance server. It supports Yjs 13, unlike the newer Yjs 14 server line. Its transport/server dependencies remain confined to this optional package; persistence is not configured. Playwright manages process teardown per run, and transport unit tests stop their own server in teardown.

Alternatives considered are Automerge and a server-authoritative service. D12 approves Yjs/y-websocket for the first recipe and its documented room/awareness protocol. Remove this integration when a replacement satisfies the same accepted semantic-delta, origin, local-history, integrity, presence and real-transport contract. The pure core integrity projection and host accepted-state APIs have no dependency on Yjs. See the [package README](../packages/collaboration-yjs/README.md) for its protocol and public APIs. Hosting, authenticated room access, durability and offline retention remain open production decisions.

# Dependency decisions

## Runtime dependencies

| Package | Owner | Reason | Removal boundary |
| --- | --- | --- | --- |
| `effect` | `packages/core` and application composition | Provides Schema-derived contracts, typed effects, services, resources, concurrency, structured logs, tracing, and release-matched OTLP modules. This is a project requirement. | None while Flow remains Effect-first. |
| `@effect/platform-bun` | Tooling applications | Supplies Effect implementations for files, paths, child processes, and the Bun runtime. It keeps tooling effects behind Effect services instead of direct host calls. | Replace when tooling moves to another supported runtime. |
| `vue` | `packages/vue` peer; `apps/vue` demo | Renders the Vue adapter and owns reactive component lifetimes, injection, and keyed DOM updates. The adapter uses Vue 3.5.43; Flow graph schemas and transitions remain in `@flow/core`. | Remove if the Vue adapter is retired; keep the runtime dependency scoped to Vue consumers rather than the core package. |
| `foldkit` | `packages/foldkit` peer; `apps/foldkit` demo | Provides the Elm-style typed Model/Message/update/view runtime for the Foldkit adapter. Version 0.163.0 requires exact `effect` and `@effect/platform-browser` 4.0.0-rc.116 peers. `@flow/foldkit` declares those peer requirements; the demo installs them directly. | Remove if the Foldkit adapter is retired; keep the runtime dependency out of `@flow/core` and other adapter packages. |
| `@effect/platform-browser` | `packages/foldkit` peer; `apps/foldkit` demo | Satisfies Foldkit 0.163.0's exact browser-platform peer. Both the adapter peer and demo dependency are pinned at 4.0.0-rc.116 to share one Effect release. | Remove with Foldkit if that adapter is retired. |
| `@effect/platform-node-shared` | Workspace tooling resolution | Pins the transitive platform shared module to 4.0.0-rc.116. `@effect/platform-bun@4.0.0-rc.116` accepts a range that also admits rc.117, which would otherwise create a mixed Effect release in the lockfile. The exact Bun package override keeps the transitive package aligned without changing any peer-dependency range. | Remove the explicit pin and override when all direct dependencies resolve matching platform modules without them. |

## Workspace package outputs

`@flow/core` ships its public JavaScript and declarations from `dist/` and declares the exact `effect` release `4.0.0-rc.116`. `@flow/vanilla` ships its public JavaScript, declarations, and stylesheet and depends on that Effect release and `@flow/core`. `@flow/vue` ships its public entry point and stylesheet, depends on `@flow/core` and Effect, and declares Vue `^3.5.43` as a peer. `@flow/foldkit` ships its public entry point and stylesheet, depends on `@flow/core` and Effect, and declares Foldkit `0.163.0` and `@effect/platform-browser` `4.0.0-rc.116` as peers. The private Vue and Foldkit demos consume their adapters through package exports; the Foldkit demo declares its runtime peers directly. `bun run test:consumer` packs all four packages, installs them into three separate clean consumers without workspace aliases or source access, checks peer resolution, typechecks public imports, and exercises host behavior, styles, and teardown in Chromium. Core is also imported by Bun with DOM globals absent. These checks cover the named fixtures; they do not establish complete feature parity or prove server-side rendering for browser adapters. The workspace root pins `@effect/platform-bun`, `@effect/platform-browser`, `@effect/platform-node-shared`, and `effect` to `4.0.0-rc.116`, matching Foldkit's exact peers and preventing a mixed Effect release in the lockfile. Vite, TypeScript, Bun, and Playwright remain workspace build or verification tools rather than runtime dependencies of the core package.

## Development dependencies

| Package | Reason | Alternatives considered |
| --- | --- | --- |
| `typescript` | Compiles strict contracts and will power source analysis without another AST dependency. | Babel and ts-morph add dependencies without supplying stronger TypeScript semantics. |
| `vite` | Builds and serves the browser host with a stable URL for Playwright. | Bun HTML serving is smaller, but Vite gives predictable browser transforms and reload behavior for the first visual slices. Reassess after the renderer stabilizes. |
| `@foldkit/vite-plugin` | Owned by `apps/foldkit`; version 0.24.0 supplies Foldkit's model-preservation handshake and view identity transforms with Vite 8 and Effect rc.116. Remove with the Foldkit host or when its development server no longer uses Vite. | Plain Vite cannot answer Foldkit's model-preservation requests; use the official plugin instead of maintaining a custom protocol handler. |
| `vitest` | Runs unit and contract tests in the Vite TypeScript environment, including browser-adjacent tests. | Bun test is smaller, but Vitest integrates directly with Vite and Playwright. |
| `@playwright/test` | Verifies the real browser output, interaction path, accessibility state, and later pixel parity. | DOM emulators cannot prove layout, pointer behavior, SVG output, or screenshots. |
| `@types/bun` | Types the selected tooling runtime. | Handwritten declarations would drift from Bun. |
| `oxlint` | Runs the Ultracite lint preset and repository-local anti-slop rules. | ESLint provides a larger plugin ecosystem but adds more startup time and dependencies than this workspace needs. |
| `@oxlint/plugins` | Loads the vendored anti-slop and anti-slop Effect JavaScript plugins. Its version matches Oxlint exactly. | Publishing or consuming anti-slop as an npm dependency would conflict with its vendored-source model. |
| `oxfmt` | Applies and checks the Ultracite formatting preset. | Prettier is mature, but Oxfmt keeps the formatter in the same Oxc toolchain as Oxlint. |
| `ultracite` | Supplies the shared Oxlint, Vitest, and Oxfmt policy used by workspace scripts. | Hand-maintained base rules would duplicate a large policy and make upgrades harder to audit. |

## Example-only dependencies

These packages serve the Download Image recipe in `apps/vanilla/ui-recipes/closing` and the layout recipes in `apps/{vanilla,vue,foldkit}/ui-recipes/layout` ([Plan 109](../plans/109-example-integrations.md)). Each app declares them as exact dev dependencies. No package under `packages/` imports them, and the `@flow/vanilla` package build bundles only `src/public.ts`, so they stay out of published code. Flow core supplies the engine-neutral input and output helpers (`getFlowLayoutInput`, `applyFlowLayoutPositions`), so a consumer can swap engines without Flow changes.

| Package | Owner | Purpose | Alternatives considered | Removal boundary |
| --- | --- | --- | --- | --- |
| `@dagrejs/dagre` 3.1.1 | The three example apps | Layered tree layout for the Dagre Tree, Auto Layout and Dynamic Layouting recipes. It ships ESM and its own types. | The unmaintained `dagre` 0.8 package needs separate types and CommonJS interop. `d3-hierarchy` lays out only trees, not general graphs. | Remove with the layout recipes, or when the recipes move to another engine. |
| `elkjs` 0.12.0 | The three example apps | ELK layered layout with fixed-position ports for the Elkjs Tree and Elkjs Multiple Handles recipes. The recipes import the bundled build, which runs on the main thread without a worker. | Dagre has no port constraints, so it cannot place edges by measured handle position. A web-worker ELK setup adds a worker URL per host for no gain at recipe size. | Remove with the ELK recipes. |
| `d3-force` 3.0.0 and `@types/d3-force` 3.0.10 | The three example apps | Force simulation for the Force Layout recipe. The recipe drives ticks from its own animation frame loop and writes positions through public edits. | A hand-written spring simulation would duplicate a well-tested solver. `d3-force` has no DOM dependency and needs no other d3 module. | Remove with the Force Layout recipe. |
| `html-to-image` 1.11.11 | Vanilla and Vue example apps (development dependency) | Download Image exports the rendered viewport to PNG, using public bounds and viewport helpers and a fitted export transform. Pinned to [React Flow’s example version](https://reactflow.dev/examples/misc/download-image), because that page reports export problems in newer versions. | A native canvas redraw needs a second renderer for custom HTML and SVG nodes. Manual SVG foreignObject serialization duplicates image, font and stylesheet embedding. html2canvas is larger. | Remove with the Download Image recipes. Never imported by a published adapter package or core. |
